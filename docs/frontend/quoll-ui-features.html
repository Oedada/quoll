Quoll — функционал интерфейса

CRM ИТ Школы Ростелекома: полный список того, что должно быть в интерфейсе, с нуля. Состояние бэкенда — ветка dev, 25.09.2026.

ВСЕАДМИНРУКОВОДИТЕЛЬМЕНЕДЖЕР — кому доступно. БЭКЕНД ПОЗЖЕ — требование из ТЗ или AS IS, API ещё нет: заложить место в интерфейсе.

Все пути API — от /api/v1, кроме входа и выхода. Авторизация — кука сессии, запросы с credentials: 'include'. Ошибки приходят как {"detail": ...}: 400 — неверный запрос, 401 — не вошёл, 403 — нет прав, 404 — не найдено, 409 — конфликт с текущим состоянием, 422 — неверные поля, 503 — недоступен Keycloak.

«Взаимодействие» = «гусеничка» = инстанс воркфлоу: работа с одним вузом по одному договору.

  1. ВСЕ Вход через Keycloak: кнопка «Войти» ведёт на GET /auth/, после входа браузер возвращается на страницу приложения.
  2. ВСЕ Выход: POST /auth/logout, затем экран входа.
  3. ВСЕ Кто я: GET /users/me — имя, логин, почта, роль, руководитель (у менеджера), активность. По роли строится меню.
  4. ВСЕ Ответ 401 на любом запросе — переход на экран входа.
  5. ВСЕ Ответ 403 «Account role mapping is inconsistent» — отдельный экран «Учётка заблокирована: неоднозначная роль, обратитесь к администратору».
  6. ВСЕ Ответ 409 «Role transition in progress» — экран «Идёт смена вашей роли, доступ временно закрыт».
  7. ВСЕ Меню по роли: менеджер — мои взаимодействия, мой статус, просьбы; руководитель — команда, пулы, взаимодействия, просьбы; админ — пользователи, воркфлоу, справочники, реестр задач, сводка.
  8. ВСЕ Уведомления в реальном времени: WebSocket ws(s)://<хост>/api/v1/ws/notifications, иконка статуса соединения, переподключение при обрыве.
  9. ВСЕ Колокольчик с числом непрочитанных и список своих уведомлений: GET /notifications/me — заголовок, текст, дата, прочитано.
  10. ВСЕ Отметить уведомление прочитанным: PATCH /notifications/{id}/read.
  11. АДМИН Все уведомления системы: GET /notifications/; отправить уведомление пользователю: POST /notifications/.
  12. ВСЕ Постраничные списки: параметры limit (до 100) и offset, кнопки «вперёд/назад».
  13. ВСЕ Устаревшие данные: 409 с текстом «… has changed, current value: …» — показать «Данные изменились» и перезагрузить карточку. Все операции со взаимодействием и оргструктурой отправляют ожидаемое текущее значение (expected_owner_id, expected_state_id, expected_superviser_id) — его берут из только что загруженной карточки.
  14. АДМИН Список пользователей: GET /users/ — логин, почта, имя, роль, активность, руководитель. Фильтр по роли пока делается на клиенте.
  15. АДМИН Карточка пользователя: GET /users/{id}.
  16. АДМИН Создать учётку: POST /users/ — логин (латиница, цифры, «_»), почта, пароль от 8 символов, имя, фамилия, роль. Подсказка: новый менеджер попадает в «Пул А», в команду его забирает руководитель, а не админ.
  17. АДМИН Изменить профиль: PATCH /users/{id} — почта, имя, фамилия. Роль здесь не меняется.
  18. АДМИН Отключить учётку (увольнение): POST /users/{id}/deactivate с подтверждением. 409 — это последний дееспособный руководитель или админ либо попытка отключить себя; 503 — недоступен Keycloak. Удаления учёток в системе нет.
  19. АДМИН Включить учётку обратно: POST /users/{id}/reactivate.
  20. АДМИН Сменить роль: PATCH /users/{id}/role {"role"}. Ответ 200 — роль сменилась сразу; 202 — «учётка заблокирована, пока руководитель не передаст её работу, затем роль применится сама». 409 — та же роль, смена уже идёт, учётка неактивна, последний руководитель или админ, своя роль.
  21. АДМИН Пределы загрузки: PATCH /org/profiles/{id}/limits — у менеджера max_active_projects, у руководителя max_subordinates, от 1 до 50. Можно опустить ниже текущей загрузки: уже взятое не отбирается.
  22. АДМИН Сводка здоровья: GET /admin/health-checks — упавшие фоновые задачи, задачи, ждущие дольше 3 дней, взаимодействия, ждущие места дольше суток, менеджеры без руководителя с работой, число дееспособных руководителей и админов. Ненулевые проблемные счётчики и ноль дееспособных — подсветить.
  23. АДМИНРУКОВОДИТЕЛЬ Реестр задач оргструктуры (увольнения, смены роли): GET /org/pending-actions — тип, кого касается, статус, попытки, последняя ошибка («осталось 3 взаимодействия к передаче»). Админ видит все, руководитель — свои и по своей команде.
  24. АДМИН Справочник вузов: список, создание, правка, удаление — /universities/. Все роли видят список.
  25. АДМИН Справочник вендоров: список, создание, правка, удаление — /vendors/. Все роли видят список.
  26. АДМИН Файлы-шаблоны: загрузка POST /attachments/ (multipart file, до лимита размера), метаданные, скачивание /attachments/{id}/download, временная ссылка /presigned-url, удаление. 409 при удалении — файл принадлежит взаимодействию.
  27. АДМИН Список воркфлоу: GET /workflows/ — название, описание, опубликован.
  28. АДМИН Создать, переименовать, изменить описание воркфлоу: POST/PATCH /workflows/.
  29. АДМИН Удалить воркфлоу — только неопубликованный: DELETE /workflows/{id}.
  30. ВСЕ Схема воркфлоу (гусеница): GET /workflows/{id} — стадии по позиции и рёбра между ними. Выделить начальную стадию (цель ребра без «откуда») и терминальные; архивные стадии показывать серыми.
  31. АДМИН Добавить стадию: POST /stages/ — название, описание, позиция, «терминальная», «занимает слот менеджера». Два последних флага после создания не меняются — предупредить в форме.
  32. АДМИН Изменить стадию: PATCH /stages/{id} — название, описание, позиция.
  33. АДМИН Удалить стадию неопубликованного воркфлоу: DELETE /stages/{id}.
  34. АДМИН Архивировать стадию опубликованного воркфлоу: POST /stages/{id}/archive — диалог подтверждения и выбор стадии, куда переедут висящие взаимодействия (по умолчанию — предыдущая). 409 — цель не подходит или граф станет непроходимым, текст причины показать.
  35. АДМИН Добавить переход (ребро): POST /transitions/ — откуда (пусто — вход в начальную стадию), куда, название, комментарий. 409 с причиной, если ребро ведёт в тупик.
  36. АДМИН Изменить переход: PATCH /transitions/{id} — название, комментарий, активен/неактивен. У опубликованного воркфлоу «откуда» и «куда» не меняются: деактивировать и создать новое.
  37. АДМИН Удалить переход — только в неопубликованном воркфлоу; в опубликованном — деактивировать.
  38. АДМИН Сменить начальную стадию одним действием: POST /workflows/{id}/start-stage {"stage_id"}.
  39. АДМИН Опубликовать воркфлоу: POST /workflows/publish/{id}. 409 — граф непроходим: нет одной начальной стадии, есть тупики или недостижимые стадии — показать текст причины.
  40. АДМИН Прикрепить к переходу файлы-шаблоны и открепить их: POST/DELETE /transitions/{id}/attachments/{attachment_id}. Шаблоны видны всем при переходе.
  41. РУКОВОДИТЕЛЬ Моя команда: GET /org/subordinates — у каждого менеджера занято слотов из максимума, незакрытых взаимодействий, «держат» (незакрытые и черновики), статус готовности («готов», «загружен», «не берёт новые», «неактивен»); занято мест в штате из квоты.
  42. РУКОВОДИТЕЛЬ Пул А — свободные менеджеры без руководителя: GET /org/managers/recruitment-pool, кнопка «Взять в команду» (POST /org/subordinates/{id}). 409 — штат заполнен или менеджера уже забрали.
  43. РУКОВОДИТЕЛЬ Пул Б — кого можно назначить на взаимодействие: GET /org/subordinates/assignment-pool. Только свои и готовые, отсортированы от наименее загруженных.
  44. РУКОВОДИТЕЛЬАДМИН Пул В — команды выбывших руководителей: GET /org/managers/orphaned; руководитель усыновляет менеджера (POST /org/subordinates/{id}/adopt), админ только видит.
  45. РУКОВОДИТЕЛЬ Открепить менеджера (вернуть в Пул А): DELETE /org/subordinates/{id}?expected_superviser_id=…. 409 с числом — у него остались незакрытые взаимодействия или черновики.
  46. РУКОВОДИТЕЛЬ Перевести своего менеджера в другую команду вместе с его взаимодействиями: POST /org/subordinates/{id}/transfer. Команду выбирать из витрины вакантных мест.
  47. РУКОВОДИТЕЛЬАДМИН Балансировка между отделами: свободные слоты у готовых менеджеров по командам (GET /org/supervisors/available-project-capacity) и вакантные места в штате по командам (/available-team-quota).
  48. ВСЕ Профиль сотрудника: GET /org/profiles/{id} — у менеджера загрузка и статус, у руководителя квота и размер команды. Менеджер видит себя, руководитель — себя и своих, админ — любого.
  49. МЕНЕДЖЕР Мой статус: загрузка, статус готовности и переключатель «Готов брать новые проекты / Не давать мне новые» — PATCH /org/profiles/me/workload.
  50. ВСЕ Список взаимодействий: GET /interactions/ с фильтрами по вузу и вендору. Каждый видит своё: менеджер — текущие и бывшие свои, руководитель — своей команды, свои черновики, бесхозные закрытые и команды выбывших руководителей, админ — все. Колонки: вуз, вендор, ИТ-программа, ИТ-продукт, владелец, стадия, пауза.
  51. РУКОВОДИТЕЛЬ Создать взаимодействие-черновик: POST /interactions/ — вуз, вендор, ИТ-программа, ИТ-продукт, воркфлоу (только опубликованный, можно позже). Подсказка: черновик видит только автор, пока не назначит менеджера.
  52. ВСЕ Карточка взаимодействия: GET /interactions/{id} — вуз, вендор, воркфлоу, текущая стадия, владелец, автор, состояние паузы, срок и причина паузы.
  53. МЕНЕДЖЕРРУКОВОДИТЕЛЬ Изменить ИТ-программу и ИТ-продукт: PATCH /interactions/{id}. Владелец, стадия и воркфлоу здесь не меняются.
  54. РУКОВОДИТЕЛЬ Удалить черновик, который ещё не вставал на стадию: DELETE /interactions/{id}. 409 — уже в работе, его закрывают, а не удаляют.
  55. РУКОВОДИТЕЛЬ Назначить или переназначить менеджера: POST /interactions/{id}/assign — менеджер из Пула Б или другой команды, причина. 409 — у менеджера нет мест, он не готов, выбыл или у него нет руководителя.
  56. МЕНЕДЖЕРРУКОВОДИТЕЛЬ Перевести на следующую стадию: кнопки из GET /transitions/available?workflow_id=…&from_stage_id=… — у черновика без стадии это вход в начальную. Действие POST /interactions/{id}/transition с комментарием. 409 — нет ответственного, стадия в архиве, у менеджера нет мест.
  57. МЕНЕДЖЕРРУКОВОДИТЕЛЬ Поставить на паузу: POST /interactions/{id}/pause — причина обязательна, срок от 1 до 720 часов или без срока. Повторная пауза заменяет текущую. Показывать состояние: «активна», «пауза до…», «пауза без срока», «срок вышел, ждёт свободного места».
  58. МЕНЕДЖЕРРУКОВОДИТЕЛЬ Снять паузу: POST /interactions/{id}/unpause. 409 — у владельца нет места.
  59. РУКОВОДИТЕЛЬ Досрочно закрыть («сделка сорвалась» и т. п.) из любой стадии: POST /interactions/{id}/close — терминальная стадия и обязательный комментарий.
  60. РУКОВОДИТЕЛЬ Переоткрыть закрытое взаимодействие: POST /interactions/{id}/reopen — менеджер, рабочая стадия, достижимая из начала, комментарий.
  61. МЕНЕДЖЕР Попросить руководителя передать взаимодействие другому менеджеру (можно предложить кого) или закрыть его досрочно (стадия закрытия и обоснование): POST /interactions/{id}/requests. 409 — такая просьба уже открыта.
  62. МЕНЕДЖЕРРУКОВОДИТЕЛЬАДМИН Список просьб: GET /requests/?status=… — вид, взаимодействие, кто просит, обоснование, статус («ждёт», «одобрена», «отклонена», «отменена»), решение. Менеджер видит свои, руководитель — своей команды, админ — все.
  63. РУКОВОДИТЕЛЬ Одобрить просьбу: POST /requests/{id}/approve — для передачи руководитель сам выбирает менеджера, предложение менеджера — только подсказка. 409 с текстом «no longer valid» — просьба устарела и отменена.
  64. РУКОВОДИТЕЛЬ Отклонить просьбу с обязательным комментарием: POST /requests/{id}/reject.
  65. МЕНЕДЖЕР Отозвать свою просьбу, пока её не решили: DELETE /requests/{id}.
  66. ВСЕ История взаимодействия: GET /interactions/{id}/history. Две ленты: движение по стадиям (откуда, куда, вид — переход, закрытие, переоткрытие, перенос при архивации; кто, когда, комментарий) и назначения (менеджер, с какого по какое время, причина). Их можно слить в одну ленту по времени на клиенте.
  67. ВСЕ Документы взаимодействия: GET /interactions/{id}/documents — название, тип, стадия, кто загрузил, когда, файл. Старые версии показывать ниже и серыми, is_current = false.
  68. МЕНЕДЖЕРРУКОВОДИТЕЛЬ Загрузить документ: POST /interactions/{id}/documents, multipart — файл, стадия (любая стадия воркфлоу этого взаимодействия), название, тип, метаданные JSON-строкой; «новая версия» — replaces_document_id заменяемого. 409 — эта версия уже заменена, стадия в архиве или у взаимодействия нет воркфлоу.
  69. ВСЕ Скачать документ и получить временную ссылку — через /attachments/{id}/download и /presigned-url. Доступ — по правам на взаимодействие.
  70. АДМИН Удалить документ: DELETE /documents/{id}. Это единственное бизнес-действие админа, с подтверждением.
  71. БЭКЕНД ПОЗЖЕ Переходы с одобрением руководителя (AS IS: шаги 3→4 и 6→7): менеджер запрашивает, руководитель одобряет или отклоняет; после отказа — возврат на корректировку документов.
  72. БЭКЕНД ПОЗЖЕ Обязательные файлы и поля на шагах: документы обмена, скан договора с номером и датой, акт передачи, срок лицензии, дата встречи, число обученных преподавателей. Без них кнопка перехода неактивна.
  73. БЭКЕНД ПОЗЖЕ Правила возвратов: менеджер — только на шаг назад и с обязательным комментарием, многошаговый возврат — руководитель; после подписания назад нельзя.
  74. БЭКЕНД ПОЗЖЕ Продукты в составе договора со статусами «предложен», «согласован», «отклонён», «активен»; после подписания состав фиксируется, расширение — через допсоглашение.
  75. БЭКЕНД ПОЗЖЕ Отдельные ветки по продуктам после подписания: шаги передачи, внедрения, обучения и обновления идут параллельно по каждому продукту, каждая ветка со своей стадией, паузой и возвратами.
  76. БЭКЕНД ПОЗЖЕ Комментарии на каждом шаге гусенички — мини-окно обсуждения на шаге (делает второй разработчик).
  77. БЭКЕНД ПОЗЖЕ Правка пройденных шагов: комментарий — свободно, с отметкой изменения на гусенице; замена файла — только с одобрения руководителя.
  78. БЭКЕНД ПОЗЖЕ Порог застоя: значение по умолчанию задаёт админ, руководитель переопределяет для своего проекта; уведомление руководителю о зависшем взаимодействии; после возврата таймер сбрасывается.
  79. БЭКЕНД ПОЗЖЕ Справочники ИТ-направлений, ИТ-продуктов, программ вузов (код, факультет, дисциплины) и контактов вуза (ответственные).
  80. БЭКЕНД ПОЗЖЕ Импорт справочников из xls/xlsx: выбор файла, настройка соответствия колонок полям, предпросмотр с ошибками по строкам, применение, отчёт об импорте.
  81. БЭКЕНД ПОЗЖЕ Отчёты за период в xls, xlsx, pdf по выбранным колонкам (вуз, ИТ-направление, ИТ-продукт, статус, ответственный); каждая роль — по своей видимости.
  82. БЭКЕНД ПОЗЖЕ Визуализация: диаграммы по воронке и загрузке с выгрузкой в png и pdf.
  83. БЭКЕНД ПОЗЖЕ Шаг 0 при создании взаимодействия: анализ совместимости продуктов с вузом — «подходит», «нужна доп. работа с преподавателями», «нужны другие продукты» — и рекомендации продуктов.
  84. БЭКЕНД ПОЗЖЕ Принятие назначения менеджером («гусеница создаётся после принятия») — пока назначение сразу делает менеджера владельцем.
  85. БЭКЕНД ПОЗЖЕ Запрос руководителя на изменение воркфлоу (переименование или удаление шага) и его одобрение или отклонение админом.
  86. БЭКЕНД ПОЗЖЕ Системный журнал действий только для админа: кто, что, когда, было — стало, с фильтрами. Журнал уже пишется, экрана и API чтения пока нет.
  87. БЭКЕНД ПОЗЖЕ Данные из LMS в карточке продукта (число студентов и потоков) и сведения с сайта вуза; настройка интеграций админом.
