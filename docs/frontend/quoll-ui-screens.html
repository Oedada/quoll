Quoll — экраны, механики и сценарии

Для фронтенда: из каких окон состоит интерфейс, что на каждом, как оно себя ведёт и через какие сценарии проходят пользователи. Дополняет чек-лист ручек quoll-ui-features.pdf; полный контракт — Swagger /docs. Состояние бэкенда — ветка dev, 25.09.2026 (редакция 2: принятие заявки, правила шагов, аппрув, откат, файлы на пройденный шаг, запросы на изменение воркфлоу).

Термины. Взаимодействие = гусеничка = работа с одним вузом по одному договору, идёт по стадиям воркфлоу. Владелец — менеджер, который его ведёт. Руководитель владельца — его непосредственный руководитель. Черновик — взаимодействие без владельца и без стадии.

Роли. МЕНЕДЖЕР ведёт свои взаимодействия. РУКОВОДИТЕЛЬ создаёт взаимодействия, раздаёт их менеджерам, собирает команду, решает просьбы. АДМИН ведёт учётки, воркфлоу и справочники; бизнес-действий не делает (единственное исключение — удаление документа). ПРОБЕЛ — нужного API нет, см. последний раздел.

1. Общая механика интерфейса

  • Каркас. Шапка: имя пользователя, метка роли, колокольчик уведомлений с числом непрочитанных, индикатор связи WebSocket, «Выйти». Слева — меню по роли. Справа от содержимого ничего постоянного нет.
  • Меню менеджера: Главная, Мои взаимодействия, Просьбы, Мой статус.
  • Меню руководителя: Главная, Взаимодействия, Просьбы, Моя команда, Набор (Пул А и Пул В), Балансировка, Реестр задач.
  • Меню админа: Сводка, Пользователи, Воркфлоу, Справочники, Файлы-шаблоны, Реестр задач, Все взаимодействия (только чтение), Уведомления.
  • Состояние сессии. При старте — GET /users/me. 401 на любом запросе — на экран входа. Сессия живёт на сервере; повторный логин не нужен, пока кука жива.
  • Кнопки по правам. Кнопки, которые пользователю недоступны, не рисуются. Но сервер — последняя инстанция: 403 на действие показывать тостом «Нет прав на это действие» и перезагружать экран.
  • Ошибки. Тост с текстом detail (он на английском — переводить по словарю из раздела 4 или показывать как есть). 422 — подсветить поля формы. 503 — «Сервис учёток недоступен, повторите через минуту».
  • Устаревшие данные. Все изменения взаимодействия и оргструктуры несут ожидаемое текущее значение (expected_owner_id, expected_state_id, expected_superviser_id) — берите его из загруженной карточки. Ответ 409 «… has changed, current value …» — жёлтая плашка «Кто-то уже изменил эти данные» и кнопка «Обновить».
  • Подтверждения. Модальное «Вы уверены?» для необратимого и чувствительного: удаление черновика, открепление, отключение учётки, смена роли, архивация стадии, публикация воркфлоу, удаление документа, досрочное закрытие.
  • Причина и комментарий обязательны в: паузе, досрочном закрытии, переоткрытии, просьбе, отклонении просьбы. Кнопка «Сохранить» неактивна, пока поле пустое.
  • Уведомления в реальном времени. WebSocket /api/v1/ws/notifications (тот же хост, та же кука). Новое сообщение — тост и +1 на колокольчике. Обрыв — индикатор серый, переподключение с отступом 1, 2, 5, 10 с. Панель колокольчика — список GET /notifications/me, клик — прочитано.
  • Списки. Постранично: limit до 100, offset. Сортировку делает сервер (взаимодействия — новые сверху; менеджеры — от наименее загруженных).
  • Без перезагрузки страницы (ТЗ): после любого действия перезапрашивать только затронутый блок. Отклик — до 1 с.

2. Экраны и окна

2.1 Вход и экраны блокировки

ВСЕ

  • Вход: логотип, кнопка «Войти через корпоративную учётку» → /auth/ (Keycloak) → возврат в приложение.
  • «Учётка заблокирована» — если 403 «role mapping is inconsistent»: в Keycloak у человека не одна роль. Текст: «Обратитесь к администратору». Кнопка «Выйти».
  • «Идёт смена роли» — если 409 «Role transition in progress»: «Ваша роль меняется. Доступ откроется, когда руководитель передаст вашу текущую работу». Кнопка «Выйти».
  • Отключённая учётка — после отключения сессии удаляются, человек получает 401 и попадает на экран входа; Keycloak его не пустит.

2.2 Главная

  • МЕНЕДЖЕР Блок «Входящие заявки» — назначенные, но ещё не принятые (owner_id = я, state_id пуст): «Принять» и «Отказаться». Карточка «Мой статус»: «Занято 3 из 5», статус готовности, переключатель «Беру новые проекты». Ниже — мои взаимодействия в работе, отдельным блоком — на паузе и «ждут места». Блок «Мои открытые просьбы».
  • РУКОВОДИТЕЛЬ Блок «Ждут решения» — просьбы команды со статусом «ждёт» (GET /requests/?status=PENDING). Блок «Команда» — полоска загрузки по каждому менеджеру и «Штат 4 из 5». Блок «Мои черновики» — созданные, но не назначенные. Блок «Нужно разобрать» — Пул В и задачи реестра.
  • АДМИН Сводка здоровья (раздел 2.19).

2.3 Список взаимодействий

ВСЕ — каждый видит своё: менеджер — текущие и бывшие свои; руководитель — своей команды, свои черновики, закрытые без владельца и команды выбывших руководителей; админ — все.

  • Таблица: вуз, вендор, ИТ-программа, ИТ-продукт, владелец, стадия, пауза (значок и «до 12.10»), дата создания.
  • Фильтры: вуз, вендор (серверные). Поиск и фильтр по стадии, владельцу, паузе — пока на клиенте в пределах страницы ПРОБЕЛ.
  • Метки строк: «Черновик» (без стадии), «Закрыто» (терминальная стадия), «Без владельца», «Бывшее моё» (у менеджера, владелец другой).
  • Кнопка «Создать» — только у руководителя, открывает окно 2.4.
  • Клик по строке — карточка 2.5.

2.4 Окно «Новое взаимодействие»

РУКОВОДИТЕЛЬ

  • Поля: вуз (выбор из справочника), вендор, ИТ-программа, ИТ-продукт, воркфлоу (только опубликованные; можно оставить пустым — выберется первым переходом).
  • Подсказка: «Черновик видите только вы, пока не назначите менеджера».
  • После создания — сразу карточка с предложением «Назначить менеджера». Назначение — это предложение: слот менеджера занимается, только когда он примет заявку.

2.5 Карточка взаимодействия — главный экран работы

  • Шапка: вуз, вендор, ИТ-программа и ИТ-продукт (редактируются на месте владельцем и его руководителем; вуз и вендор — тоже), владелец с аватаром, автор, воркфлоу, плашка паузы с причиной и сроком.
  • Гусеница: горизонтальная лента стадий воркфлоу по позиции (GET /stages/by-workflow/{id}): пройденные — закрашены (по истории), текущая — выделена, будущие — контуром, терминальные — отдельным цветом, архивные — скрыты. Рёбра — из GET /workflows/{id}. Клик по стадии — история и документы этой стадии.
  • Панель действий — кнопки зависят от роли и состояния, матрица ниже.
  • Вкладки: Документы (2.12), История (2.13), Просьбы по этому взаимодействию.

2.6 Окно «Назначить менеджера»

РУКОВОДИТЕЛЬ

  • Список «Свои готовые» — Пул Б (GET /org/subordinates/assignment-pool): ФИО, «занято 2 из 5», сортировка от наименее загруженных — первого подсвечивать как рекомендацию.
  • Если все свои заняты — блок «Свободные места в других командах» (/org/supervisors/available-project-capacity) с подсказкой передать руководителю той команды. Выбрать конкретного менеджера чужой команды пока нельзя ПРОБЕЛ.
  • Поле «Причина» (необязательно). Отправка — POST /interactions/{id}/assign c expected_owner_id из карточки.
  • Ошибки: 409 «capacity exhausted» — «У менеджера нет свободных мест»; «not accepting new projects» — «Менеджер не берёт новые проекты»; «has no supervisor» — «У менеджера нет руководителя»; 503 — Keycloak недоступен.

2.6а Окно «Принять заявку» и «Отказаться»

МЕНЕДЖЕР-владелец

  • «Принять»: вход в начальную стадию — POST /interactions/{id}/accept с to_stage_id (цель ребра из GET /transitions/available?workflow_id=… без from_stage_id) и необязательным комментарием. Если у заявки нет воркфлоу — сначала выбрать опубликованный.
  • 409 «capacity exhausted» — «Нет свободных мест: освободите слот или откажитесь».
  • «Отказаться»: POST /interactions/{id}/decline, комментарий обязателен. Заявка вернётся автору черновиком без владельца. От принятой так не отказываются — только просьбой о передаче (409).
  • Обычный переход из черновика отвечает 409 «The owner starts the interaction by accepting it».

2.7 Окно «Перевести на стадию»

МЕНЕДЖЕРРУКОВОДИТЕЛЬ

  • Кнопки доступных переходов: GET /transitions/available?workflow_id=…&from_stage_id=…. У черновика без стадии — вход в начальную стадию; если у черновика нет воркфлоу, предложить выбрать опубликованный воркфлоу, затем его вход.
  • Клик по переходу — окно: название перехода, куда, комментарий, файлы-шаблоны этого перехода (скачать), кнопка «Перевести».
  • Ошибки: «Assign a manager before moving» — «Сначала назначьте менеджера»; «No active transition» — «Такого перехода больше нет» + обновить; «archived» — «Стадия в архиве»; «capacity» — «Нет свободных мест у владельца»; 409 про стадию — плашка устаревших данных.
  • Перевод в терминальную стадию снимает паузу и отменяет открытые просьбы — предупредить.
  • Свойства ребра (приходят в ребре): requires_approval — кнопка превращается в «Попросить аппрув» (окно 2.11, вид «Пройти шаг»); is_backward — «Вернуть на шаг назад», комментарий обязателен (иначе 422), руководитель получит уведомление; required_document_kinds — перечислить в окне, какие файлы нужны, и отметить уже приложенные.
  • Шаг не доделан — 409 «Step is not done: …» со списком через «; »: пустые обязательные поля (required field 'number' is empty), нет файла нужного типа (no current document of kind 'signed_contract'). Показать списком и дать перейти к полям и документам.

2.7а Панель «Поля шага»

МЕНЕДЖЕРРУКОВОДИТЕЛЬ — правка; ВСЕ — чтение

  • Описание полей — у стадии: fields = [{key, label, type, required}], типы string, text, date (ISO «2026-09-01»), number, bool. Рисовать форму по описанию, обязательные — со звёздочкой.
  • Значения: GET /interactions/{id}/stage-values — по всем стадиям; сохранение — PUT /interactions/{id}/stage-values/{stage_id} с {values: {...}} целиком (не слиянием).
  • Править можно текущий шаг и пройденные («число обученных» дописывают со временем); у будущих — 409 «Stage is not reached yet». Неверный тип или лишнее поле — 422 с перечнем.
  • На пройденном шаге с изменёнными после прохождения значениями — значок «изменено» (сравнить updated_at со временем выхода из стадии по истории).

2.7б Окно «Откатить»

РУКОВОДИТЕЛЬ владельца

  • Выбор стадии из тех, где взаимодействие уже было после последней точки невозврата (по истории: записи после перехода по ребру с is_irreversible), комментарий обязателен. POST /interactions/{id}/rollback с to_stage_id, expected_state_id, comment.
  • 409 «Rollback goes only to a stage passed after the point of no return» — после подписания договора назад в первую часть нельзя.
  • Данные шагов и файлы не стираются; в истории — запись вида «Откат».

2.8 Окно «Пауза»

МЕНЕДЖЕРРУКОВОДИТЕЛЬ

  • Причина (обязательно). Переключатель «До даты» / «Без срока»; дата-время от +1 часа до +30 дней, с часовым поясом.
  • На уже приостановленном — кнопка «Изменить паузу» (замена срока или режима) и «Снять паузу».
  • Состояние «Срок вышел, ждёт места»: система сама снимет паузу, когда у владельца освободится слот. Кнопка «Снять вручную» — 409, если мест нет.
  • Черновик без стадии и закрытое на паузу не ставятся — кнопки нет.

2.9 Окно «Досрочно закрыть»

РУКОВОДИТЕЛЬ владельца

  • Выбор терминальной стадии этого воркфлоу («Завершено», «Сделка сорвалась» и т. п.) и обязательный комментарий. Ребро в графе не нужно — закрыть можно с любого шага.
  • После закрытия слот менеджера освобождается, пауза снимается, открытые просьбы отменяются.
  • Менеджер вместо этой кнопки видит «Попросить закрыть» (окно 2.11).

2.10 Окно «Переоткрыть»

РУКОВОДИТЕЛЬ

  • Менеджер (свои готовые; можно прежнего), рабочая стадия воркфлоу (нетерминальная), обязательный комментарий.
  • Ошибки: «not reachable from the start» — «В эту стадию нельзя вернуться: к ней нет пути от начала»; 403 — «Это закрытый проект чужой команды»; ёмкость — как в 2.6.

2.11 Окно «Просьба руководителю»

МЕНЕДЖЕР-владелец

  • Вид: «Передать проект» (по желанию — кому хотел бы передать, из менеджеров), «Закрыть досрочно» (терминальная стадия) или «Пройти шаг» — аппрув перехода (kind: "TRANSITION", target_stage_id — цель ребра с аппрувом).
  • Для «Пройти шаг» поля и файлы проверяются сразу: не доделано — 409 со списком, как у перехода. Ребро без аппрува — 400.
  • Обоснование (обязательно).
  • Одновременно может быть открыта одна просьба каждого вида; 409 — «Такая просьба уже ждёт решения».
  • После отправки — в карточке плашка «Ваша просьба ждёт решения руководителя» и кнопка «Отозвать».

2.12 Вкладка «Документы» и окно загрузки

  • ВСЕ Список (GET /interactions/{id}/documents), сгруппированный по стадиям: название, тип, файл, кто загрузил, когда. Цепочка версий: актуальная сверху, прежние — ниже и серым («уходит вниз, сереет, но не пропадает»).
  • ВСЕ Скачать (/attachments/{id}/download) или открыть по временной ссылке (/presigned-url).
  • МЕНЕДЖЕРРУКОВОДИТЕЛЬ Окно загрузки: файл, стадия (по умолчанию текущая, можно любую стадию воркфлоу), название (по умолчанию имя файла), тип (строка: договор, акт, протокол…), доп. сведения (ключ-значение → JSON). Действие «Новая версия» у документа открывает то же окно с replaces_document_id — название и тип подставятся из прежней.
  • Ошибки: «already replaced» — «Эту версию уже заменили, замените актуальную»; «archived» — «Стадия в архиве»; «no workflow yet» — «Сначала переведите взаимодействие в первую стадию»; 413 — файл слишком большой.
  • АДМИН «Удалить» у документа — только он, с подтверждением; цепочка версий сошьётся сама.
  • Файл не на текущий шаг от менеджера приходит со status: "PENDING" и is_current: false — метка «Ждёт одобрения». Руководитель получает уведомление и решает: POST /documents/{id}/approve или /reject (комментарий по желанию). Отклонённый (REJECTED) остаётся в списке серым и выходит из цепочки версий — прежняя версия снова актуальна. Файл руководителя сразу ACTIVE.
  • Для обязательных файлов шага считаются только ACTIVE и актуальные версии.

2.13 Вкладка «История»

ВСЕ — кто видит взаимодействие

  • Единая лента по времени из двух списков GET /interactions/{id}/history: движение по стадиям и назначения.
  • Стадии: «Переход: Встреча → Документы», «Досрочно закрыто», «Переоткрыто», «Перенесено при архивации стадии», «Отказ в аппруве», «Откат» — кто, когда, комментарий.
  • Назначения: «Назначен Иванов (причина)», «Передано Петрову», с периодом ведения.
  • Имена стадий — из /stages/by-workflow/{id}, людей — из справочника GET /org/people?ids=…&ids=… (ФИО, роль, активность; любому вошедшему).

2.14 Экран «Просьбы»

  • Таблица GET /requests/: вид, взаимодействие, кто просит, предложенный менеджер или стадия закрытия, обоснование, статус, решение и комментарий. Фильтр по статусу.
  • РУКОВОДИТЕЛЬ «Одобрить»: для передачи — выбор менеджера (предложенный менеджером подставлен, но выбирает руководитель), комментарий. 409 «no longer valid» — «Просьба устарела (сменился владелец, взаимодействие закрыто или стадия в архиве) и отменена» + обновить. 409 по ёмкости цели — просьба остаётся, выбрать другого.
  • РУКОВОДИТЕЛЬ «Отклонить» с обязательным комментарием. У аппрува шага отказ может сам увести взаимодействие на доработку (стадия reject_to_stage_id ребра) — в истории запись «Отказ в аппруве». После доработки менеджер просит аппрув заново.
  • РУКОВОДИТЕЛЬ Одобрение аппрува выполняет переход от его имени. Если взаимодействие уже ушло с шага или ребро отключили — 409 «Request is no longer valid», просьба отменена.
  • МЕНЕДЖЕР «Отозвать» свою ждущую.

2.15 Экран «Моя команда»

РУКОВОДИТЕЛЬ

  • Индикатор «Штат 4 из 5». Таблица (GET /org/subordinates): ФИО, полоска «занято 3 из 5», незакрытых, «держат» (незакрытые и черновики), статус готовности цветной меткой.
  • «Открепить» (вернуть в Пул А) — только при нуле «держат», иначе 409 «Manager still has N…» — показать «Сначала передайте N взаимодействий».
  • «Перевести в другую команду» — выбор команды из витрины вакантных мест; менеджер уходит вместе со своими взаимодействиями.
  • Клик по менеджеру — профиль (2.18) и его взаимодействия.

2.16 Экран «Набор»

РУКОВОДИТЕЛЬ (вкладку «Пул В» видит и АДМИН)

  • Вкладка «Пул А — свободные»: менеджеры без руководителя, в строю; кнопка «Взять в команду». Менеджер со статусом «не беру новые» тоже доступен для набора.
  • Вкладка «Пул В — осиротевшие»: менеджеры, чей руководитель уволен или в смене роли; колонка «прежний руководитель»; кнопка «Усыновить».
  • Ошибки: «Team is full» — «Штат заполнен»; устаревшие данные — «Менеджера уже забрали».

2.17 Экран «Балансировка»

РУКОВОДИТЕЛЬАДМИН

  • Две таблицы: «Свободные слоты у готовых менеджеров» по командам и «Вакантные места в штате» по командам; своя команда в них не показывается.
  • Назначение: куда предложить проект или перевести человека, когда в своей команде мест нет.

2.18 Профиль сотрудника и «Мой статус»

  • ВСЕ Профиль (GET /org/profiles/{id}): ФИО, роль, активность, у менеджера — загрузка и статус готовности, у руководителя — квота и размер команды. Менеджер видит себя, руководитель — себя и своих, админ — всех.
  • МЕНЕДЖЕР «Мой статус»: переключатель «Беру новые проекты / Не давать мне новые» (PATCH /org/profiles/me/workload). «Не давать» не снимает текущие проекты — только закрывает назначение новых. Можно включить «беру» и при полной загрузке — статус покажет «загружен».

2.19 Админ: сводка

  • Шесть плиток (GET /admin/health-checks): упавшие фоновые задачи; ждут человека дольше 3 дней; взаимодействия ждут места дольше суток; менеджеры без руководителя с работой; дееспособных руководителей; дееспособных админов. Проблемные счётчики больше нуля — оранжевым, ноль дееспособных — красным.
  • Плитки кликабельны: задачи → реестр, менеджеры → пользователи.

2.20 Админ: пользователи

  • Таблица (GET /users/): логин, почта, ФИО, роль, активность, руководитель. Фильтр по роли и поиск — на клиенте ПРОБЕЛ.
  • «Создать»: логин, почта, пароль, ФИО, роль. Подсказка: новый менеджер попадает в Пул А.
  • «Изменить»: почта, ФИО.
  • «Отключить» / «Включить» с подтверждением. Отключение — это увольнение: сессии сбрасываются, в реестре появляется задача «передать портфель». 409 — последний дееспособный руководитель или админ, отключить себя.
  • «Сменить роль»: выбор роли, подтверждение. 200 — «Роль изменена». 202 — «Учётка заблокирована до передачи работы; роль применится автоматически» + ссылка на задачу в реестре.
  • «Пределы»: для менеджера — максимум проектов, для руководителя — максимум людей в команде, 1–50.

2.21 Админ: воркфлоу и редактор графа

  • Список воркфлоу: название, опубликован, число стадий; «Создать», «Переименовать», «Удалить» (только черновик).
  • Редактор: слева — стадии по позиции (перетаскивание меняет позицию), справа — граф: стадии узлами, рёбра стрелками, начальная — отдельной меткой, неактивные рёбра пунктиром, архивные стадии скрыты или серые.
  • Стадия: создать (название, описание, «терминальная», «занимает слот» — два последних после создания менять нельзя, предупредить), переименовать, удалить (черновик) или «Архивировать» (опубликованный) — окно выбора стадии, куда переедут висящие взаимодействия.
  • Ребро: создать (откуда — или «вход», куда, название, комментарий), переименовать, «Деактивировать» / «Активировать». У опубликованного концы не меняются; удаления нет — только деактивация.
  • Правила ребра (меняются и у опубликованного): «Нужен аппрув руководителя» (не на входе — 400), «При отказе увести на…» (только вместе с аппрувом), «Возврат назад», «Точка невозврата», «Обязательные типы файлов» (список строк).
  • Поля стадии: конструктор списка «ключ латиницей, подпись, тип, обязательное»; ключи уникальны. Поля меняются и у опубликованного, флаги «терминальная» и «занимает слот» — нет.
  • «Сделать начальной» у стадии — одно действие.
  • «Опубликовать» — у черновика. 409 с причинами: «нужна ровно одна начальная», «из стадий X нет пути к завершению», «стадии Y недостижимы» — показать списком и подсветить на графе.
  • После любой правки опубликованного граф проверяется сервером; 409 с причиной — правка не применена.
  • У ребра — прикреплённые файлы-шаблоны: «Прикрепить из библиотеки», «Открепить».

2.21а Запросы на изменение воркфлоу

  • РУКОВОДИТЕЛЬ «Предложить изменение» у воркфлоу: свободный текст — POST /workflow-change-requests/. Список своих — GET /workflow-change-requests/?status=.
  • АДМИН Список всех ждущих; «Одобрить» / «Отклонить» с комментарием. Саму правку админ делает в редакторе — кнопка «Открыть редактор» рядом. Автор получает уведомление о решении.

2.22 Админ: справочники и файлы-шаблоны

  • Вузы и вендоры: таблица, «Добавить», «Изменить», «Удалить» (409, если используется).
  • Библиотека файлов-шаблонов: загрузка, скачивание, удаление; привязка к рёбрам — из редактора. Файлы взаимодействий здесь не удаляются (409).
  • Импорт реестра взаимодействий из xls/xlsx: POST /interactions/import (файл, workflow_id, dry_run). Сначала «Проверить» (dry_run=true), потом «Загрузить». Ответ — по номерам строк: created, skipped (уже есть) и ошибки с колонкой. Каждое созданное взаимодействие предлагается менеджеру из колонки ФИО — он его принимает.

2.23 Реестр задач оргструктуры

АДМИН — все; РУКОВОДИТЕЛЬ — свои и по своей команде

  • Таблица (GET /org/pending-actions): тип («увольнение менеджера», «увольнение руководителя», «смена роли»), кого касается, статус, попытки, последняя причина ожидания («осталось 3 взаимодействия к передаче», «ещё включён в Keycloak»), создана.
  • Задачи выполняются сами в фоне; действия в реестре нет — руководитель разбирает портфель в карточках, и задача завершается.

3. Сценарии

3.1 Запуск нового проекта с вузом

  1. Руководитель: «Взаимодействия» → «Создать» → вуз, вендор, продукт, воркфлоу → черновик.
  2. В карточке черновика: «Назначить» → менеджер из Пула Б.
  3. Менеджер видит заявку во «Входящих»: «Принять» (встаёт в начальную стадию, занимает слот) или «Отказаться» с причиной — тогда заявка вернётся руководителю черновиком.
  4. Дальше — переходы по гусенице (3.2).

3.2 Ведение по гусенице

  1. Менеджер открывает карточку, прикладывает документы к нужной стадии.
  2. Заполняет поля шага, прикладывает нужные файлы, жмёт доступный переход — стадия меняется, в истории запись. Не доделано — список того, чего не хватает.
  3. Шаг с аппрувом (подготовка документов → подписание, внедрение → обучение): «Попросить аппрув». Руководитель одобряет — взаимодействие переходит; отклоняет — уходит на корректировку, после неё просить снова.
  4. Что-то пошло не так — «Вернуть на шаг назад» с комментарием (руководитель узнает). На несколько шагов — просит руководителя, тот делает «Откатить».
  5. Нужно заменить файл на уже пройденном шаге — загрузка новой версии, она ждёт одобрения руководителя.
  6. Вуз попросил подождать — «Пауза» с причиной и сроком; слот менеджера освобождается.
  7. Срок вышел — система снимает паузу сама; если мест нет — «ждёт места» и снимет, как только освободится.
  8. Последний переход — в терминальную стадию: взаимодействие закрыто.

3.3 Досрочное закрытие

  1. Менеджер: «Попросить закрыть» → стадия «Сделка сорвалась», обоснование.
  2. Руководитель на «Главной» видит просьбу → «Одобрить» (закрывается) или «Отклонить» с комментарием.
  3. Руководитель может закрыть и сам, без просьбы, кнопкой «Закрыть досрочно».

3.4 Передача проекта

  1. Менеджер: «Попросить передать», по желанию предлагает кому.
  2. Руководитель одобряет и выбирает менеджера (или переназначает сам без просьбы).
  3. Новый владелец видит взаимодействие; прежний — видит его в списке как «бывшее моё», только чтение.

3.5 Переоткрытие

  1. Руководитель открывает закрытое → «Переоткрыть» → менеджер, рабочая стадия, комментарий.
  2. Взаимодействие снова в работе у выбранного менеджера, в истории — «Переоткрыто».

3.6 Сбор команды

  1. Админ заводит учётку менеджера — тот в Пуле А.
  2. Руководитель: «Набор» → Пул А → «Взять в команду» (если есть место в штате).
  3. Лишнего — «Открепить» (после передачи его работы) или «Перевести» в команду с местами.

3.7 Увольнение менеджера

  1. Админ: «Отключить». Сессии менеджера сброшены, в реестре — задача «увольнение менеджера».
  2. Руководитель видит задачу («осталось N взаимодействий») и переназначает каждое на других менеджеров.
  3. Когда передано последнее — задача завершается сама, место в штате освобождается.
  4. Закрытые взаимодействия уволенного остаются видны руководителям.

3.8 Уход руководителя

  1. Админ отключает руководителя (если он не последний дееспособный).
  2. Его менеджеры появляются в Пуле В у всех руководителей; его команды видны всем руководителям на чтение.
  3. Другие руководители усыновляют менеджеров; задача «увольнение руководителя» завершится, когда команды не останется.

3.9 Смена роли

  1. Админ: «Сменить роль».
  2. Нет работы старой роли — роль сменилась сразу, человек перелогинится с новыми правами.
  3. Есть работа — 202: учётка заблокирована (экран «Идёт смена роли»), руководитель передаёт работу, затем роль применяется сама.

3.10 Настройка воркфлоу

  1. Админ создаёт воркфлоу, добавляет стадии, рёбра, отмечает начальную.
  2. «Опубликовать» — сервер проверит проходимость и назовёт проблемы.
  3. Живой воркфлоу правится: новый шаг — стадия и рёбра к ней; убрать шаг — «Архивировать» с выбором, куда переедут взаимодействия.

3.11 Менеджер перегружен

  1. Менеджер: «Мой статус» → «Не давать мне новые».
  2. Он пропадает из Пула Б; текущими проектами продолжает заниматься.
  3. Руководитель в балансировке ищет свободные места в других командах.

5. Пробелы бэкенда, в которые упрётся фронт

  • ПРОБЕЛ Нет списка менеджеров чужой команды для руководителя — нельзя выбрать конкретного человека при межотдельской передаче; есть только сводка свободных мест по командам.
  • ПРОБЕЛ Список взаимодействий фильтруется только по вузу и вендору; нет фильтров по стадии, владельцу, паузе, поиска и общего числа записей.
  • ПРОБЕЛ Список пользователей без фильтра по роли, поиска и общего числа.
  • ПРОБЕЛ Уведомления из домена пишутся пока только для возврата на шаг назад, файла на одобрение и решения по запросу на изменение воркфлоу — и только в список (GET /notifications/me), в сокет не толкаются. Назначение, просьбы, решения по просьбам, увольнение — ещё не уведомляют.
  • ПРОБЕЛ Нет правки полей существующего документа (название, тип, метаданные) — только новая версия.
  • ПРОБЕЛ Ещё нет: ветки по продуктам после подписания и допсоглашение, комментарии на шагах, порог застоя, справочники продуктов и программ, отчёты, журнал аудита для админа, шаг 0 с рекомендациями, данные LMS, встроенная документация.
