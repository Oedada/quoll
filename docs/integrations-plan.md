# Интеграции с заглушками: план

*28.09.2026. Основа: `docs/2709/integration-contract-v0.5.md` (контракт, дальше К) и модель v1.3, п. 3.16, 3.19, 3.20, 8. Контракт сверен с кодом `dev @ 6a3c0e2`. Где он устарел, ниже сказано, что берём вместо него.*

Цель — закрыть все места, где код ссылается на данные интеграций. Сами интеграции — заглушки в базовом варианте: внешние системы (сайт, LMS) имитируются внутри процесса, всё остальное (приём, сопоставление, очередь, запросы, журнал, отчёты) работает по-настоящему.

## 0. Что уже есть и что устарело в контракте

- Уже в коде:
  - программа (`it_programs`) с `site_course_id` и `priority`;
  - вуз с `inn`, `kpp`, регионом и городом, уникальность по «ИНН + КПП»;
  - на ветке `teachers_trained` (значение КАМа) и `transfer_status`;
  - `no_return_at`, допсоглашения, виды документов.

  Пункт К §9 «чего нет в коде» в основном закрыт.
- Где в коде стоят заглушки:
  - в отчётах `students`, `streams`, `teachers_lms` всегда `None`, а в «Итого» LMS не считается (`reports/service.py`, `render.py`, `schemas.py`, В1 в `reports-design.md`);
  - у карточки ветки нет статистики LMS;
  - у `interaction_requests` нет видов `CREATE_INTERACTION` и `ADD_PROGRAM`, а `interaction_id` у них обязателен;
  - нет таблиц статистики LMS, сопоставлений, очереди несопоставленных, записей с сайта и журнала обменов;
  - нет выгрузки Э.
- Устарело в К:
  - демо-ID в §8 и приложении Б (вуз 17, ветки 201…) нашей базе не соответствуют. Заглушки строят данные из текущей базы (§3), а примеры из `docs/2709/*.json` годятся только для ручной загрузки;
  - `workflow.client_type` в коде нет — в Э отдаём константу `B2B`.

## 1. Решения по умолчанию (подтвердить)

| # | Вопрос | Решение |
|---|---|---|
| Р1 | Включать ли В1 (записи на обучение с сайта) | Да, минимально: таблица записей с отпечатком email, на заявки и воркфлоу не влияет. Выключается настройкой |
| Р2 | Кто получает выгрузку Э | Только админ, как весь раздел «Интеграции» (К §5) |
| Р3 | Транспорт заглушек | В процессе, без HTTP. Заглушка LMS отдаёт статистику по парам из последней полученной И1, заглушка сайта — записи по программам из последней И2. Числа детерминированные, от хэша ключа |
| Р4 | С каким воркфлоу создаётся заявка по `CREATE_INTERACTION` | Воркфлоу выбирает руководитель в теле одобрения, как при обычном создании |
| Р5 | `ADD_PROGRAM` после подписания | Одобрение только фиксирует решение и уведомляет КАМа: дальше он оформляет ДС на 4.1, ветку сам запрос не создаёт (К §4) |

## 2. Данные — одна миграция

| Таблица | Поля | Ограничения |
|---|---|---|
| `lms_stats` | `university_id` (CASCADE), `program_id` (CASCADE), `students`, `streams` ≥ 0, `teachers_trained` ≥ 0 или NULL, `source` LMS/FILE, `updated_at` | UNIQUE (вуз, программа) |
| `site_enrollments` | `order_number` UNIQUE, `program_id` (CASCADE), `stream`, `enrolled_on`, `source` SITE/FILE, `email_fingerprint` char(64), `created_at`, `updated_at` | ПДн не хранятся |
| `integration_mappings` | `kind` COURSE/UNIVERSITY/PROGRAM, `external_key` (нормализованная строка), `target_id`, `created_by`, `created_at` | UNIQUE (kind, external_key) |
| `integration_unmatched` | `flow` B1/B2, `code` INT-404/409, `dedupe_key`, `record` JSONB (запись без ПДн; у В1 вместо email — отпечаток), `candidates` JSONB, `status` PENDING/APPROVED/REJECTED, `decided_by`, `decided_at`, `created_at` | частичный UNIQUE (flow, dedupe_key) WHERE PENDING |
| `integration_runs` | `flow` I2/I1/B1/B2/EXPORT, `trigger` SCHEDULE/MANUAL/FILE, `status` RUNNING/DONE/FAILED, `started_at`, `finished_at`, `counters` JSONB {код: число}, `error`, `actor_id`, `payload` JSONB (что приняла заглушка у И1/И2) | частичный UNIQUE (flow) WHERE RUNNING — «кнопка неактивна» |
| `interaction_requests` | виды `CREATE_INTERACTION`, `ADD_PROGRAM`; `interaction_id` NULL допустим только у `CREATE_INTERACTION`; новые `university_id`, `program_id` (обязательны у двух новых видов) | CHECK на виды; частичный UNIQUE (kind, university_id, program_id) WHERE PENDING |

События журнала `INTEGRATION_RUN`, `TRAINING_STATS_CHANGED`, `INTEGRATION_MAPPING_RESOLVED`, актор — SYSTEM, кроме решений админа. В журнал идут только ID и ключи.

Новые настройки:
- `integration_email_key` — секрет для HMAC, в `example.env`;
- `integration_enrollments_enabled` (Р1);
- `integration_stub_available` — имитация INT-503;
- `integration_hour` — ночной час обмена по BUSINESS_TZ.

## 3. Заглушки — `integrations/stubs.py`

- `LmsStub`:
  - `push_i1(snapshot)` запоминает снимок в `integration_runs.payload`;
  - `fetch_b2()` строит записи по парам «вуз × программа» из последнего принятого И1: `students`, `streams`, `teachers_trained` детерминированно из хэша пары, а у части пар `teachers_trained` нет.
- `SiteStub`:
  - `push_i2(catalog)` запоминает каталог;
  - `fetch_b1()` строит по 1–3 записи на программу из последней И2: номер заказа от хэша, фиктивные ФИО, email и телефон. Они проверяют, что ПДн отбрасываются.
- При `integration_stub_available = false` любой вызов заглушки бросает `StubUnavailable` и даёт INT-503.

## 4. Потоки — `integrations/flows.py`

Общий каркас `run(flow, trigger, actor_id, records=None)`:
1. Вставить `integration_runs` RUNNING. Если запуск уже идёт — конфликт уникальности, 409.
2. Получить записи из заглушки или из файла.
3. Каждая запись обрабатывается в своём savepoint: сбой одной записи не валит остальные.
4. Подсчитать коды и завершить DONE.
5. При INT-503 статус FAILED, данные не меняются.
6. Итог пишется в журнал `INTEGRATION_RUN`.

По потокам:
- **И2.** Каталог программ по К §2.4, сортировка по приоритету (1 — первая, NULL в конце), затем по названию.
- **И1.** Подписанные (`no_return_at` задан) и незакрытые заявки с открытыми ветками, поля по К §2.3.
- **В1** (К §2.1, §3):
  - `null` или нет обязательного поля — INT-422;
  - сначала отпечаток, потом ФИО, телефон и email отбрасываются;
  - программа ищется по `program_id`, иначе по сопоставлению COURSE, иначе по нормализованному названию. Не найдена — INT-404 в очередь, несколько — INT-409;
  - дальше upsert по номеру заказа; те же данные — INT-208.
- **В2** (К §2.2, §3, §4):
  - вуз ищется по `id`, иначе по «ИНН + КПП», иначе по одному ИНН, если такой вуз один, иначе по сопоставлению UNIVERSITY;
  - если `id` и ИНН указывают на разные вузы — INT-409;
  - программа ищется по `id`, иначе по `site_course_id`, иначе по сопоставлению PROGRAM;
  - две записи одной пары в файле — обе INT-409;
  - дальше upsert `lms_stats`. Без изменений — INT-208, иначе пишется `TRAINING_STATS_CHANGED` со старыми и новыми числами. Если `teachers_trained` нет, прежнее значение сохраняется;
  - предложения:
    - у вуза нет незакрытой заявки → `CREATE_INTERACTION` и уведомление всем руководителям;
    - заявка есть, а неудалённой ветки этой программы нет → `ADD_PROGRAM` и уведомление руководителю ответственного КАМа;
    - оба случая дают INT-202;
    - на пару одно ждущее предложение, отклонённое повторно не создаётся.
- **Э** (К §2.5). Поля И1 плюс поля §2.5. `lms_stats` — по паре, `teachers_trained` — КАМа. Файл JSON отдаётся сразу, запуск пишется в журнал.

Ночной обмен: `Periodic` раз в `integration_interval`. В `integration_hour`, если сегодня ещё не было запусков SCHEDULE, идёт И2 → И1 → В1 → В2. Параллельные процессы разводит уникальный индекс RUNNING.

## 5. Очередь несопоставленных и предложения

Очередь:
- `GET /unmatched`;
- `POST /unmatched/{id}/resolve {target_id}`: создаёт сопоставление по ключу записи и заново прогоняет запись, аудит `INTEGRATION_MAPPING_RESOLVED`;
- `POST /unmatched/{id}/reject`.

Бизнес-данные админ не правит.

Предложения идут через существующий `request_service`, решает руководитель:
- `CREATE_INTERACTION`:
  - одобрить может любой руководитель, тело — `workflow_id` (Р4);
  - создаётся заявка с этим руководителем как автором и черновая ветка программы без продукта;
  - если у вуза уже появилась незакрытая заявка — 409.
- `ADD_PROGRAM`:
  - одобряет руководитель владельца;
  - до подписания добавляется черновая ветка через `contract_service.draft_branch`;
  - после подписания только уведомление КАМу (Р5).
- Отклонение — REJECTED.

## 6. Потребители

- **Отчёты.**
  - `students`, `streams`, `teachers_lms` берутся из `lms_stats` по паре ветки. У строки без ветки — «—».
  - «Итого» по LMS — сумма по уникальным парам среди строк.
  - Правка В1 и О6 в `reports-design.md`.
- **Карточка ветки.** `BranchRead.lms_stats` — `{students, streams, teachers_trained, updated_at}` или `null`.

## 7. API — `/api/v1/integrations`, только админ (INT-403)

| Метод | Путь | Смысл |
|---|---|---|
| GET | `/runs?flow=` | журнал запусков, последний по каждому потоку |
| POST | `/runs/{flow}` | запустить обмен вручную (I2, I1, B1, B2) |
| POST | `/upload/{flow}` | загрузить JSON для B1/B2. Файл не хранится; не JSON или не массив — INT-400 |
| GET | `/stub/{flow}` | что приняла заглушка при последнем И1/И2 (для показа) |
| GET | `/unmatched`, POST `/unmatched/{id}/resolve`, `/reject` | очередь |
| GET | `/export` | выгрузка Э с фильтрами `university_ids`, `program_ids`, `include_closed` |

Предложения LMS: `GET /proposals`, `POST /proposals/{id}/approve`, `/reject` - решает руководитель (§9, О1).

## 8. Тесты (бережливо)

Проверяются:
- приложение Б на своих данных;
- ПДн не попадают в БД и журнал;
- повтор даёт INT-208;
- параллельный запуск даёт 409;
- INT-503 не меняет данные;
- предложения не дублируются;
- одобрение `CREATE_INTERACTION` и `ADD_PROGRAM` до и после подписания;
- колонки и «Итого» LMS в отчёте;
- поля И1, И2 и Э.

## 9. Как сделано: отклонения от плана

| # | План | Сделано | Почему |
|---|---|---|---|
| О1 | `CREATE_INTERACTION` и `ADD_PROGRAM` - новые виды `interaction_requests` | Своя таблица `integration_proposals` и `integrations/proposals.py` | У просьб заявка обязательна, и на ней держатся блокировки, права и одобрение. У предложения заявки может не быть, а у одобрения своя логика (создать заявку или ветку). Смешать - значит переписать протестированный `request_service` ради двух видов |
| О2 | Очередь: ждущая запись одна на ключ | Одна на запись (`record_key`: номер заказа или пара ключей). Решение админа по ключу разбирает все ждущие записи с ним | Иначе вторая запись с тем же неизвестным курсом терялась бы до следующего обмена, а файл повторно не приходит |
| О3 | Недоступная заглушка - 503 | Запуск записывается FAILED с `{"INT-503": 1}` и возвращается с кодом 200; так же любой сбой обмена (`{"ERROR": 1}`), данные обмена откатываются | Ошибка ответа откатила бы и саму отметку о сбое. Админ видит последний обмен и повторяет его (К §6) |
| О4 | `integration_runs` со статусом RUNNING и уникальным индексом | Обмен потока держит advisory-блокировку транзакции (`flows._hold`), строка запуска пишется по итогу (DONE/FAILED). Второй запуск - сразу 409 | Строка RUNNING в той же транзакции никому не видна, а в отдельной - зависает при падении процесса. Блокировка транзакции отпускается сама |
| О5 | Два одинаковых ключа пары в файле В2 - обе INT-409 | Так и сделано, но в очередь такие записи не идут | Сопоставлением это не решить: правят файл |
| О6 | Статистика LMS в карточке ветки | `GET /interactions/{id}/branches`, поле `lms_stats` | Отдельной ручки на одну ветку нет |
| О7 | Итог обмена | Код `ERROR` - сбой разбора одной записи, остальные идут дальше | В К §6 такого случая нет |
| О8 | Отклонённое предложение по паре не пересоздаётся (К §4) | Так и сделано - навсегда, в том числе для будущих заявок вуза. Одобренное ADD_PROGRAM после подписания не повторяется по той же заявке, пока КАМ не оформит ДС | Иначе руководителю приходило бы одно и то же каждую ночь |
