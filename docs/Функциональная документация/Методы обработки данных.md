# Методы обработки данных

## Импорт каталогов (xls, xlsx)

Вход. Один файл xlsx, xls, csv или json, листы в строгом порядке: Направления, Вендоры, Продукты, Программы, Специальности, Вузы, Специальности вузов, Контакты вузов, Реестр. Загружает администратор. Пример: demo-data.xlsx (раздел 14.3).

1. Загрузка файла.
2. Сопоставление: листы и колонки распознаются по названию и синонимам («Вендоры», «Поставщики» и др.).
3. Разбор: списки в ячейке через «;» или «,»; даты ДД.ММ.ГГГГ или ГГГГ-ММ-ДД; телефоны очищаются от скобок и тире; пустые строки пропускаются.
4. Сопоставление с базой: вендор по названию, продукт по названию и вендору, вуз по ИНН + КПП, программа по названию и направлению.
5. Проверка (dry-run): отчёт по ошибкам по строкам (коды IMP в приложении А). Без записи в базу: исправьте файл и загрузите снова.
6. Реестр: строка = ветка, несколько строк одного вуза = одна заявка. Строка задаёт шаг, лицензию и передачу (раздел 5.5).
7. Запись: транзакция на весь импорт. Ошибки не ломают базу. Логируется в журнал действий.

## Отчёт за период

Вход. Период [A; B], по умолчанию: с 1 января текущего года по сегодня; фильтры: вузы, регионы, направления, программы, продукты, ответственные, статус.

Алгоритм:

1. Строка отчёта - ветка заявки. Единица счёта задаётся переключателем: «по веткам» (по умолчанию) или «по договорам» (одна строка на заявку).
2. Срез на дату B строится по истории событий: статус заявки и веток, шаг, ответственный восстанавливаются на момент даты B. Прошлый период не меняется задним числом при дальнейшей работе.
3. Шаг на дату B: для заявки - последний шаг перехода на дату B или раньше; для ветки - шаг последнего перехода ветки с отметками «пауза» и «идёт допсоглашение».
4. Ответственный - это КАМ на дату B по истории назначений; если КАМ менялся в периоде - «ФИО (ранее был: ФИО)», если его нет - «КАМ не назначен».
5. Фильтры: внутри фильтра - ИЛИ, между фильтрами - И, пустой - без ограничения. Статус - на дату B; по КАМу строка находится, если он вёл заявку хотя бы часть периода. Видимость - см. Раздел 3; права проверяются на сервере и при предпросмотре, и при выгрузке.
6. Студенты, потоки и «Обучено преподавателей (LMS)» - это одно число на пару «вуз × программа», одинаковое у всех её веток; «Обучено преподавателей (КАМ)» - у каждой ветки своё.

Выход. Предпросмотр первых 50 строк и счётчик строк; выгрузка xls, xlsx или pdf. Файл строится в фоне, скачивается автоматически и хранится 24 часа. Журнал выгрузки пишется в журнал действий.

Граничные случаи:
• Период за один день: A = B - срез на этот день.
• Заявка без веток (на шагах 0–4) при единице счёта «по веткам» показывается одной строкой с пустыми полями программы и продукта.
• Если заявка закрыта в периоде, её статус восстанавливается на дату B: если закрыта до даты B - «Закрыта» с причиной, если после - статус на тот момент.

## Показатели и диаграммы

Вход. Те же период [A; B] и фильтры, что и для отчёта.

Алгоритм:
1. Плитки и диаграммы Д1–Д7 пересчитываются по тем же отфильтрованным строкам среза.
2. Время - это медиана в днях, время на паузе исключается.
3. Линии порогов: общий порог застоя на Д2, лимит заявок КАМа на Д3.
4. Студенты и потоки это суммы по уникальным парам «вуз × программа»; между собой они не складываются.
5. Смена фильтров пересчитывает всё без перезагрузки за ≤ 1 секунду.

Граничные случаи:
• Если две ветки одной программы в вузе по 120 студентов - их в сумме 120, а не 240.
• Если заявка закрыта после подписания - она считается только своими ветками; если в Д5 ветка без продукта - она в столбце «без продукта».
• Ветка берёт дату из поля «Подписание лицензии»; если оно пусто - в Д4 она не попадает.

## Застой, ранжирование, подсказка на шаге 0

### Застой

Вход. Заявка (до подписания) или ветка (после подписания), дата начала отсчёта, порог.

Алгоритм:
1. Порог - свой у заявки, если его задал руководитель, иначе общий от администратора, по умолчанию 14 дней. У ветки — порог её заявки.
2. В застое, если «сегодня − начало отсчёта» > порога; дни календарные. Сброс отсчёта, пауза и уведомления описаны в разделе 4.4.

Выход. Признак «в застое» и одно уведомление КАМу и руководителю (раздел 4.4). «Зависли» - тот же расчёт на дату B.

Граничные случаи:
• Ветки считаются отдельно; допсоглашение их застой не сбрасывает.
• На паузе отсчёт останавливается; при снятии паузы отсчёт продолжается (или начинается заново, см. 4.4).

### Ранжирование программ

Вход. Все активные программы из справочника.

Алгоритм:
1. Программы сортируются по ручному приоритету (1 - наивысший, 2, 3...; без приоритета - в конце).
2. При равенстве приоритетов - по числу обучающихся студентов (из статистики LMS по уникальным парам «вуз × программа»).
3. При равенстве студентов - по алфавиту названия программы.

Выход. Упорядоченный список программ в каталоге, при выборе на шаге 0 и в выгрузке И2 для сайта (раздел 7.1).

### Подсказка на шаге 0

Вход. Выбранный вуз на шаге 0 создания заявки.

Алгоритм:
1. Из справочника специальностей вуза берутся специальности с тегами ИТ-направлений.
2. Для каждой программы CRM считает число совпавших специальностей вуза с её направлением.
3. Программы сортируются по этому числу по убыванию; при равенстве — по ручному приоритету, затем по названию (раздел 6.4.2). Рядом - совпавшие специальности.
4. Всё считается в CRM по справочнику, без ИИ и выхода в интернет.

Выход. Подсказка на экране шага 0; на заявку не влияет и в ней не сохраняется.

Граничные случаи:
• Специальность с несколькими направлениями засчитывается программам каждого из них.
• Если у вуза нет специальностей в справочнике - подсказка не показывается, на экране выходит «Нет данных о специальностях вуза».

## Сопоставление данных интеграций

Вход. Данные LMS по паре «вуз × программа»: студенты, потоки, обученные преподаватели. С сайта приходят записи людей на курсы: номер заказа, курс, поток. Форматы и расписание обмена находятся в разделе 7.

Алгоритм:
1. Вуз: внутренний ID CRM из выгрузки для LMS -> «ИНН + КПП» -> только ИНН, если вуз с ним в CRM один.
2. Программа: внутренний ID CRM -> у LMS ID курса, у сайта название курса после нормализации (регистр, кавычки, пробелы) -> сопоставления, которые запомнил администратор.
3. Дубли: ключ LMS - пара «вуз × программа», сайта - номер заказа. Если те же данные - «без изменений»; если изменились - обновление, старые и новые числа пишутся в журнал; если две записи одной пары в файле - обе неоднозначны.
4. Данные LMS:
  – у вуза есть незакрытая ветка программы -> обновляется статистика пары;
  – нет незакрытой заявки -> статистика сохраняется, всем руководителям - запрос «создать заявку»; подтвердивший становится автором заявки;
  – заявка есть, программы в ней нет -> руководителю ответственного КАМа отправляется запрос «добавить программу»: до подписания ветка добавляется в состав черновиком, после - только допсоглашением.
  На пару есть одно ждущее предложение, отклонённое повторно не создаётся.
5. Не найдено или неоднозначно -> очередь у администратора: «Сопоставить» (сопоставление запоминается и дальше применяется само) или «Отклонить». Бизнес-данные администратор не правит.
6. Записи с сайта заявку не создают - вуза в записи нет. ФИО и телефон отбрасываются при приёме; из email сразу считается отпечаток (хэш с секретным ключом), сам email не хранится; уникальных обучающихся = число разных отпечатков.

Выход. Статистика пары одна на все ветки программы в вузе; записи с сайта; запросы руководителям; очередь несопоставленных; итог обмена по кодам (приложение А). В журнале лежат только ID и ключи, без ФИО, телефона и email.

Граничные случаи:
• Если пришёл только ИНН, а вузов с ним несколько, или ID и «ИНН + КПП» указывают на разные вузы: запись в очередь; статистика разных вузов не суммируется.
• Обученные преподаватели: LMS пишет только своё значение и не трогает значение КАМа; если поля нет, прежнее сохраняется; в отчёте видны оба.
• Обмен никогда не меняет шаг заявки или ветки.
• Если заглушка недоступна - данные не меняются, видны время последнего обмена и кнопка «Повторить».
