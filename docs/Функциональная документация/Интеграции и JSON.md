# Интеграции и JSON

## Потоки

Запуск. Происходит раз в сутки ночью, порядок И2 → И1 → В1 → В2: сначала отдаём наши ID, потом принимаем данные с ними. Администратор проделывает следующий путь: «Запустить обмен» по потоку, «Загрузить JSON» для В1 и В2. Выгрузку Э делают КАМ, руководитель и администратор из раздела отчётов, каждый в пределах своей видимости (раздел 3.1).

Формат: UTF-8, файл - JSON-массив, ID - целые (у сотрудника это строка из Keycloak), даты - ГГГГ-ММ-ДД, дата-время - ISO 8601 с часовым поясом. И1 и И2 это полный снимок, получатель заменяет им прежний. ПДн: В1 - ФИО и телефон отбрасываются, email превращается в отпечаток; В2, И1, И2 - без ПДн; в Э - только ФИО ответственного сотрудника. Поля - в примерах приложения Б.

| Поток | Что передаётся → что происходит |
| --- | --- |
| В1 сайт →<br>CRM | Записи на курсы в формате файла заказчика «Данные оплат.json» → запись на<br>обучение, заявка не создаётся |
| В2 LMS →<br>CRM | Студенты, потоки, обученные преподаватели по паре «вуз × программа» →<br>статистика LMS или запрос руководителю |
| И1 CRM →<br>LMS | Подписанные заявки с открытыми ветками и нашими ID → LMS возвращает ID в В2 |
| И2 CRM →<br>сайт | Каталог ИТ-программ с ручным приоритетом → сайт сортирует курсы, присылает<br>наш ID программы в В1 |
| Э CRM →<br>файл | Результирующий JSON (раздел 7.5) → запись в журнал действий |

## Ключи связи с БД и хранилищем

| Объект | Ключ в JSON | Что это |
| --- | --- | --- |
| Заявка,<br>ветка,<br>продукт,<br>вендор | application_id, branches[].id, product.id, vendor.id | ID в БД |
| Вуз | university.id; запасной - inn + kpp | ID в БД; вуз уникален по ИНН + КПП (раздел<br>5.1) |
| Программа | program.id; запасной - site_course_id | ID в БД; ID курса на сайте и в LMS |
| Сотрудник | responsible.id | ID пользователя в Keycloak |
| Документ | documents[].id, storage_key, replaces | ID в БД; ключ файла в S3 - уникальное имя<br>вида attachments/<id>.pdf, связь с заявкой и<br>шагом хранится в БД; ID предыдущей версии |
| Договор,<br>допсоглашен<br>ие | contract.document_id, supplementary_agreements[].id, branches[].origin | Документ; допсоглашение, из которого<br>выросла ветка |

## Заглушки и переход на реальный API

ТЗ предусматривает контракт API от заказчика, но его не выдали: заказчик предложил работать на заглушках, организаторы сообщили, что доступа к API не будет. Поэтому формат обмена задан в решении. Заглушки отдают файлы В1, В2 и сохраняют принятые И1, И2.

При переходе на реальный API не меняются ключи (раздел 7.2), сопоставление, очередь и запросы руководителю (раздел 6.5), коды INT, расписание и журнал действий. Меняется источник - API сайта и LMS вместо заглушки, добавляется авторизация во внешних системах; если контракт заказчика отличается от нашего формата, на входе добавляется сопоставление полей. Методы обмена описаны в Swagger UI (раздел 10)

## Допущения

Подтверждаются у заказчика при подключении реальных API:
• с сайта приходят только записи людей на курсы, в формате «Данные оплат.json» (B1);
• LMS хранит и возвращает наши ID вуза и программы, ID курса у сайта и LMS общий; без ID - запасной ключ вуза ИНН + КПП, программы — ID курса или название;
• обученные преподаватели в LMS считаются по программе; значение КАМа по ветке хранится отдельно;
• «Статус по передаче» - «Передано» / «Не передано» (раздел 5.5)

## Результирующий JSON и интеграция в Enterprise

Результирующий JSON - это заявки по фильтрам отчёта: вуз, ответственный, шаг, договор, допсоглашения, документы, ветки с программой, продуктом, лицензией и статистикой, плюс ключи из 7.2. Пример в приложении Б.5.

Интеграция в Enterprise: сервис отдельный, методы - в Swagger UI (раздел 10), вход осуществляется через Keycloak (раздел 11). Внешней системе хватает наших ID из выгрузки или запасных ключей - ИНН + КПП, ID курса.
