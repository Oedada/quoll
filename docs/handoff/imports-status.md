## Что сделано за все три захода

### Применение (коммит 2, этот заход)

1. **`place.py`** (§19 целиком) - `apply_group(session, batch, an, plan)`, единица применения - группа реестра:
   - `_share_stages` - FOR SHARE на все целевые стадии группы (заявки, веток, AGR, DONE, стадии закрытия заменяемой) раньше блокировки заявки, по возрастанию id (§17.4 п.2 - как ход ветки);

   - создание заявки `project_service.create_interaction`, `UPDATE branches SET created_at = earliest` (В25), назначение `assign_locked(announce=False, assigned_at=earliest)`;
   - постановка на шаг `transition_service.place_imported` и подписание `contract_service.seal_imported` (готовы с коммита 2, здесь - подключены и дополнены отметками «пройден» для ленты ветки, В27 - `contract_service.seal_imported(branch_start_id=...)`, `transition_service._stages_between(..., branch=True)`);
   - договор (§19.7) - `_attach_contract`: файл вида CONTRACT строки → документ с вложением; только номер → документ без вложения, `title = «Договор №<номер>»`; продление - `_extend_contract` через `bindings.current_contract`;
   - пауза открытых веток (`branch_service.pause_locked`, новый метод - выделен из `pause` по образцу `project_service.pause_locked`), пауза заявки (`project_service.pause_locked`), В8-закрытие (`transition_service.close_locked(by_import=True)`);
   - комментарии строк → история `COMMENT` (ветки или заявки), файлы строк → документы (`_apply_files`, без CONTRACT - тот отдельно), контакты группы → каталог вуза (`_apply_contacts`, **только вариант CATALOG**, см. «Отклонения»);

   - `interaction.slot_changed_at = now()` (В28), журнал `INTERACTION_IMPORTED`.
2. **`worker.py`** - обход групп реестра после каталогов: `_pending_groups` (по возрастанию номера первой строки), `_group_unit`/`_apply_group` - тот же паттерн, что у строки каталога (`_unit`/`_apply`): перепроверка статуса всех строк группы под блокировкой (M3), savepoint, `result`/`result_ids`/`result_code` на все строки группы разом; `_attempt` обобщён на список id (попытка считается по первой строке единицы, как в §17.3).

## Что не сделано (сознательные отклонения от дизайна)

1. **Динамические поля шага «step:\*»** (§19.2, §19.9 `STEP:<stage_id>:<key>`) - в `mapping.py`/`spec.py` нет источника для таких колонок вообще (REGISTRY - фиксированный набор полей, привязки к произвольному полю шага воркфлоу не разбираются). Это не пробел коммита 2 - источника нет уровнем выше, в анализе. `place.py` эти значения не пишет; `step_service._upsert`/`_journal`, которые дизайн просит звать по одному на (стадия, ветка), сейчас не вызываются вовсе.
2. **Контакты группы (§19.9)** - реализован только вариант `CATALOG` (создание/обновление контакта вуза по «ФИО, телефон, email» из поля «Ответственные от ВУЗа»). Вариант `STEP:<stage_id>:<key>` (ссылка в значения шага) невозможен без п.1; `contacts_target` в `RowPatch` принимается API, но в `place.py` не используется - выбор пользователя между «в каталог» и «в поле шага» сейчас всегда равносилен «в каталог».
3. **Файл строки → документ, стадия по умолчанию** (§19.8) - вместо полной таблицы (поиск ближайшего `required_document_kinds` по рёбрам от шага ветки) взят упрощённый выбор: явный `stage_id` файла, иначе стадия ветки строки (`b.stage_id`) или стадия заявки (`plan.stage_id`); ошибка `IMP-184` (стадия не пройдена и не текущая) не проверяется - документ создаётся на вычисленной стадии без сверки с историей.
4. **Договор: расхождение номера** (§19.7, `IMP-178` «файл и строка расходятся, побеждает файл») - анализ (`registry.py`) не сравнивает номер из файла CONTRACT с номером из колонки; `place.py` берёт номер группы (`plan.contract_number`), при наличии файла - его реквизиты, если у файла они заданы, иначе групповые. При обоих источниках разошедшихся молча побеждает значение колонки, а не файл - обратный дизайну приоритет. Предупреждение `IMP-178` нигде не ставится.
5. **Гонка REPLACE под блокировками** (§17.4 п.3, `InteractionChangedConcurrentlyException` → три попытки) - `lock_interaction_scope` уже умеет это сама (общий механизм), отдельно в `place.py` не тестировалось: нет теста с двумя реальными соединениями по образцу `test_sa_races.py` на сценарий «менеджера сменили между чтением и захватом во время REPLACE».
6. **Тесты §26** - написаны п.5 (REPLACE, частично - только (а)-конфликт с черновиком, не (б)-закрытая заявка), п.9 (M3 - перепроверка группы под блокировкой, через `_apply_group`/`_group_unit`), 15 (M1 - REPLACE), 18 (SAME-скип). Не написаны: п.6 (доп. поля целиком - допсоглашение, продление лицензии/договора, пауза ветки), 11 (отчёты - `IMPORT` в «Переходах», хотя код изменён), 14 (уведомления `IMPORT_ASSIGNED`), 16-17 (M6/M14 - гонки), 19-23 (В27 отметки «пройден» отдельным тестом, В28 бездействие, M11/M12/M16/M18 применительно к группе - общий механизм для строки каталога уже покрыт `test_import_apply.py`, для группы - только «в среднем работает» через 4 теста выше, не «доказано по каждой гарантии»).
7. **`docs/import-errors.md`** - строковые замечания (§22.2) по-прежнему без пользовательских формулировок «что делать» (см. вопрос 2 ниже, не решался в этом заходе).

## Правила пользователя

Вопросы - пользователю, критичное не решать самому. Коммиты - одна короткая строка по-английски в повелительном наклонении, без тела. Комментарии в коде - по-русски, коротко, тире «-», без «ёлочек»; сообщения исключений - по-английски. KISS/DRY, в чужие модули - только по необходимости. Тесты - в `backend/tests_stage1` ветки `tests-imports` (не в `backend/tests`). Postgres локально: контейнер `backend-postgres-1` (`docker exec backend-postgres-1 psql -U quoll ...`) - в этом окружении systemd/`pg_ctl` нет, база живёт в docker compose.
