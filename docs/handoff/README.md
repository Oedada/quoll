# Бриф для параллельного разработчика (cloud session)

Ты работаешь параллельно с основной командой. Основная команда сейчас доделывает **Этап 1**:
- блок C — воркфлоу, закрытие, переоткрытие, просьбы менеджера, документы заявки;
- блок D — фоновые процессы, увольнение, смена роли, сверка с Keycloak.

Твоя зона — **заготовки Этапов 2, 3 и 6 и инфраструктура** в новых модулях и новых файлах. Задачи подобраны так, чтобы при слиянии не было конфликтов. Правила из раздела 4 — не пожелания, а условие, при котором это работает.

---

## 1. Что за продукт

**quoll** — CRM ИТ Школы Ростелекома. Система ведёт работу с вузами по внедрению ИТ-продуктов по «гусенице» из 14 шагов: от поиска контакта в вузе до повышения квалификации преподавателей.

Источники требований лежат в `docs/`. Бизнес-логику мы **не придумываем**, а берём оттуда:

| Файл | Что там |
| :--- | :--- |
| `6. ИТ Школа Ростелекома.md` | официальное ТЗ: 14 шагов, каталоги, отчёты, интеграции |
| `qA.md` | Q&A с заказчиком, 46 пунктов уточнений |
| `алеоп оп оп опля оп .md` | разбор шагов «гусеницы» аналитиком: файлы на шагах, возвраты, аппрувы |
| `бдыщ.md` | роли, справочники, аудит |
| `AS_IS_—_процесс_и_роли_—_CRM_ИТ_Школы_РТК.md` | процесс «как есть» от команды |
| `quoll-gap-analysis-and-roadmap.md` | дорожная карта Этапов 1–6 |
| `quoll-stage2-6-questions.md` | открытые вопросы по Этапам 2–6 с рекомендациями |

**Роли:**
- **менеджер** ведёт вузы и двигает заявки;
- **руководитель** назначает менеджеров и владеет оргструктурой;
- **админ** ведёт справочники, воркфлоу и учётки, но бизнес-действий не выполняет.

## 2. Как запустить

```bash
cd backend
cp example.env .env          # SESSION_SECRET_KEY сгенерировать, команда в файле
docker compose up -d         # postgres 16, keycloak 26, garage (S3 на :3900)
uv sync --all-groups
uv run alembic upgrade head
uv run uvicorn quoll.main:app --reload
```

- Демо-страница — `http://localhost:8000/front`, вход через Keycloak под `admin`/`admin`.
- Swagger — `/docs`.
- Проверка кода: `uv run ruff check src` и `uv run ruff format <твои файлы>`.

## 3. Как устроен код (повторяй, не изобретай)

**Стек:** FastAPI 0.141, SQLAlchemy 2 async, asyncpg, Postgres 16, Alembic, pydantic 2, Keycloak (OIDC), S3 через aioboto3.

**Модуль:** `src/quoll/<модуль>/` с файлами:
- `models.py`, `schemas.py`, `repository.py`, `service.py`, `router.py`, `dependencies.py`;
- `*_policy.py` — чистые правила без обращений к БД;
- `__init__.py` — экспортирует роутер.

**Слои:**
- роутер — HTTP, DTO и права через зависимости;
- сервис — сценарий и транзакция;
- репозиторий — запросы;
- политика — чистые функции.

В роутере не пишется SQL, в сервисе не бросается `HTTPException`.

**Кирпичи, которые используй как есть:**

| Что | Где |
| :--- | :--- |
| сессия БД | `from quoll.db import SessionDep`. Коммит делается сам, **до отправки ответа** (`scope="function"`). Сам не коммить |
| база моделей | `quoll.db.Base`, `quoll.core.mixins.IdMixin`, `TimestampMixin`, `quoll.db.str_255` |
| CRUD | `quoll.core.base_repository.BaseRepository` |
| кто вошёл | `quoll.auth.dependencies`: `CurrentUser`, `AdminUser`, `SupervisorUser`, `ManagerUser`, `AdminOnly` |
| ошибки | `quoll.core.exceptions`: `AppException`, `DomainRuleException(status, detail)`, `IdNotExistsException`. Тексты ошибок — на английском |
| журнал действий | `quoll.auth.audit.record(session, actor_id=..., event_type=..., target_type=..., target_id=..., old_value=..., new_value=...)`. Журнал только на добавление |
| что видит пользователь из заявок | `quoll.interactions.access_policy.readable_filter(user)` — SQL-условие. Только читать |
| граф воркфлоу | `quoll.workflows.workflow_service`: `create_stage`, `create_transition`, `change_start_stage`, `publish`; `quoll.workflows.graph_policy.graph_problems` |

**Правила и конвенции:**
- **Роутеры** регистрируются под `/api/v1/...` с `dependencies=[Depends(get_current_user)]` на уровне роутера. Тест основной команды перебирает все маршруты: незащищённый маршрут уронит сборку.
- **Схемы на запись** — `model_config = ConfigDict(extra="forbid")`: лишнее поле даёт 422, а не молча игнорируется.
- **Комментарии** — по-русски, коротко, со строчной буквы, только про неочевидное, без «ёлочек».
- **Коммиты** — одна короткая строка по-английски, без трейлеров.

**Грабли, на которые мы уже наступили:**
- **Ленивые связи в async.** Дёрнуть ленивую связь в async-коде нельзя (`MissingGreenlet`). Читай явно или через `selectinload`. После записи, если в ответе есть поле, которое ставит сервер (`updated_at`), делай `await session.refresh(obj)`.
- **CHECK на существующей таблице** Alembic при автогенерации не видит — дописывай руками. Каждую миграцию проверяй циклом `upgrade head` → `downgrade -1` → `upgrade head` → `alembic check`.
- **Секреты из одних цифр** в docker compose бери в кавычки.

## 4. Правила стыковки — чтобы не было конфликтов

### 4.1 Запретные зоны: эти файлы и модули не трогай

| Зона | Почему |
| :--- | :--- |
| `src/quoll/interactions/**` | блок C: закрытие, переоткрытие, просьбы, документы, права |
| `src/quoll/workflows/**` | правка графа, архивация стадий — блок C |
| `src/quoll/attachments/**` | политика чтения вложений — блок C |
| `src/quoll/org/**`, `src/quoll/auth/**`, `src/quoll/core/**` | оргструктура и блок D |
| `src/quoll/notifications/**` | зона Оедады |
| комментарии к шагам | зона напарника |
| `frontend/auth-demo.html` | демо ведёт основная команда |
| существующие миграции в `alembic/versions/` | история ревизий |

Если без правки в чужой зоне никак, **остановись и опиши в отчёте**, что нужно и почему. Основная команда внесёт сама.

### 4.2 Разрешённые точки касания — минимально и по шаблону

1. **`src/quoll/main.py`** — только `import` твоего роутера и строка `app.include_router(...)`. Добавляй **в самый конец** блока подключений, отдельной группой с комментарием `# этапы 2-6`.
2. **`src/quoll/auth/audit_models.py`** — только новые значения `AuditEventType` и `TargetType`, **в конце перечислений**, отдельным блоком с комментарием `# каталоги`.
3. **`pyproject.toml`** — новые зависимости через `uv add` (например, `openpyxl`, `reportlab`). `uv.lock` при слиянии пересоберём.
4. **Миграции** — только новые файлы. Первая твоя ревизия ставится на голову, которая была на момент старта (`uv run alembic heads`). Если к слиянию у нас появятся свои ревизии, мы добавим merge-ревизию. Ревизии на наши таблицы не делай.
5. **Связи с чужими таблицами** — только внешним ключом из твоей таблицы: `university_id → universities.id`, `vendor_id → vendors.id`. **Не добавляй** `relationship`/`back_populates` в модели `University`, `Vendor`, `Interaction`: это правка чужого файла.

### 4.3 Тесты

У основной команды тесты лежат в отдельной ветке, которой у тебя нет. Поэтому:
- твои тесты — в `backend/tests_catalog/`. Каталог `backend/tests/` занят `.gitignore`;
- `docs/handoff/conftest_reference.py` и `factories_reference.py` — образцы наших фикстур: отдельная тестовая база, накатанная миграциями, откат каждого теста через savepoint, вход через `login_as(user)`, Keycloak подменён. Скопируй и поправь импорты;
- запуск: `cd backend && uv run pytest tests_catalog -q` (нужен `docker compose up -d`);
- **требования к тестам:** e2e через HTTP-клиент с минимумом моков, граничные случаи, права на каждую роль. После каждого теста проверяй, что он ловит поломку: сломай код и убедись, что тест падает.

## 5. Задачи

Порядок — по зависимостям. Каждая задача — отдельный коммит или серия коммитов. Где бизнес-правило не утверждено, бери **рекомендацию** из `quoll-stage2-6-questions.md` и помечай в коде и в отчёте: «по рекомендации, ждёт подтверждения». Спорное **не решай молча** — выпиши в отчёт.

### Задача 1. Модуль справочников `catalog` (Этап 2)

Новый модуль `src/quoll/catalog/`.

**Модели и миграция:**

| Таблица | Поля | Ограничения |
| :--- | :--- | :--- |
| `it_directions` | `name` | уникальное имя |
| `products` | `name`, `description`, `vendor_id` → `vendors.id` (nullable, RESTRICT), `direction_id` → `it_directions.id` (nullable, SET NULL), `keywords` (JSONB, список строк), `is_active` | уникальный `name` в пределах вендора |
| `university_programs` | `university_id` → `universities.id` (CASCADE), `name`, `code` (например, «09.03.02»), `faculty`, `disciplines` (JSONB, список), `keywords` (JSONB, список) | уникальный `(university_id, code, name)` |
| `university_contacts` | `university_id` (CASCADE), `full_name`, `position`, `department`, `email`, `phone`, `is_primary`, `is_actual` | частичный уникальный индекс: один `is_primary` на вуз среди `is_actual` |

- Всем моделям — `IdMixin`, `TimestampMixin`.
- Поле `universities.contacts` (JSON) **не трогай**: перенос старых контактов — отдельный вопрос в отчёт.

**API** под `/api/v1/catalog/...`:
- чтение — любой вошедший;
- запись — только админ (`AdminOnly`);
- CRUD на каждую сущность, списки с `limit`/`offset` и фильтрами (`university_id`, `vendor_id`, `direction_id`, `q` — поиск по имени через `ILIKE`);
- удаление продукта, на который кто-то ссылается, — 409, а не 500.

**Журнал.** Каждая мутация пишется через `record`. Добавь свои `TargetType.PRODUCT`, `PROGRAM`, `CONTACT`, `DIRECTION` и события `CATALOG_ITEM_CREATED`, `CATALOG_ITEM_UPDATED`, `CATALOG_ITEM_DELETED` по правилу 4.2.

**Тесты:**
- права: менеджер и руководитель на записи получают 403;
- уникальность;
- каскад при удалении вуза;
- поиск и фильтры;
- пагинация: фильтр применяется до `limit`;
- 422 на лишнее поле.

### Задача 2. Импорт справочников из xls/xlsx с маппингом (ТЗ, раздел «Каталоги», п. 1)

**Что нужно.** ТЗ требует обновлять справочники загрузкой файлов xls/xlsx «по согласованному маппингу полей». Колонки исходного реестра: Название вуза, Вендор, ПО, Номер договора, Подписание лицензии, Срок действия лицензии (год), Статус по передаче, ФИО менеджера, Ответственные от вуза, Комментарий.

**Реализация:** `catalog/importer.py` на `openpyxl`, а для `.xls` — `xlrd` или просьба пересохранить в xlsx; выбери и обоснуй.

**Эндпоинты:**
- `POST /api/v1/catalog/imports/preview` (multipart: файл и `mapping` в JSON: «колонка файла → поле»). Возвращает первые N разобранных строк и ошибки **по строкам**, в базу ничего не пишет;
- `POST /api/v1/catalog/imports` с тем же телом. Применяет изменения и возвращает отчёт: сколько создано, обновлено, пропущено, ошибки со строками.

**Что создаётся:**
- **в справочниках** — вузы (по имени, upsert), вендоры, продукты («ПО»), контакты вуза («Ответственные от вуза» — разбор ФИО и должности, если получится);
- **договорные колонки** (номер договора, лицензия, срок, статус передачи, ФИО менеджера, комментарий) **заявки не создают**: это домен блока C и назначений. Они ложатся «как есть» в новую staging-таблицу `catalog_import_rows` (`import_id`, `row_number`, `raw` JSONB, `university_id`, `vendor_id`, `product_id`, `created_at`) плюс таблица `catalog_imports` (кто, когда, файл, маппинг, итоги). Перенос в заявки сделаем потом.

**Правила:**
- импорт — одна транзакция: ошибка строки не роняет импорт, но и не пишет эту строку;
- повторный импорт того же файла идемпотентен по справочникам;
- лимит размера — как `MAX_UPLOAD_SIZE_MB` в настройках;
- только админ;
- в журнал — `CATALOG_IMPORTED` с итогами.

**Тесты:** настоящие xlsx-файлы, собранные в тесте через `openpyxl`:
- маппинг с перестановкой колонок;
- пустые и битые строки;
- повторный импорт;
- preview ничего не пишет;
- не-админ получает 403;
- слишком большой файл получает 413.

### Задача 3. Эталонный воркфлоу «гусеницы» как данные (заготовка Этапа 3)

**Что нужно.** Файл `backend/seed/reference_workflow.yaml` описывает стадии и рёбра эталонного воркфлоу по ТЗ (14 шагов) и разбору аналитика (`алеоп…md`). Скрипт `backend/scripts/seed_reference_workflow.py` загружает его **через функции `workflow_service`**, не мимо них: `create_stage` → `create_transition` → `change_start_stage` → `publish`. Нужна сессия и id админа для журнала.

**Как составить граф:**
- шаги ТЗ 1–14; B2C-вариант — отдельный воркфлоу, если в Q&A хватит данных;
- рёбра «вперёд» по регламенту и развилка 4 → 5 → 6 / 4 → 6 (вопрос 3.1, бери рекомендацию);
- возврат на один шаг назад — **только до подписания** (шаг 6 ТЗ): после подписания назад нельзя («ПОСЛЕ ШАГА 4 выполненного… вообще нельзя назад» в разборе аналитика);
- терминальные стадии: «Завершено» и «Отказ / Сделка сорвалась». Рёбра в «Отказ» **не заводи**: досрочное закрытие идёт отдельной операцией без ребра, а ребро «в отказ отовсюду» позволило бы менеджеру закрывать самому, мимо руководителя;
- `consumes_capacity`: реши по смыслу — встреча и ожидание вуза не должны занимать слот менеджера. Обоснование — в комментарии YAML.

**Правила:**
- скрипт идемпотентен: воркфлоу с таким именем уже есть — выйти с сообщением;
- граф проходит `graph_problems(..., full=True)` без замечаний. Сделай на это тест.

**Не делай:** правила возвратов с обязательным комментарием, обязательные файлы на шагах, аппрувы — это движок Этапа 3, его проектирует основная команда. Всё, что ты заметил в источниках про такие правила, выпиши списком в отчёт.

### Задача 4. Отчёты по взаимодействиям (ТЗ «Отчёты»)

**Что нужно.** Новый модуль `src/quoll/reports/`:
- `GET /api/v1/reports/interactions?date_from=&date_to=&columns=...&format=xlsx|xls|pdf`;
- колонки по ТЗ: вуз, ИТ-направление, ИТ-продукт, статус (стадия), ответственный, плюс дата создания и последнего перехода.

**Правила:**
- **видимость** — строго через `readable_filter(current_user)`: менеджер видит свои, руководитель — свою команду и т. д. Своих правил видимости не пиши;
- **период** — по `interactions.created_at` или по дате записи в `interaction_stage_history`; выбери, обоснуй, сделай параметром;
- **только чтение**: никаких записей в наши таблицы;
- xlsx — `openpyxl`, pdf — `reportlab`. Кириллица в pdf обязательна, нужен TTF-шрифт в репозитории — проверь лицензию шрифта;
- ИТ-направление и продукт появятся из задачи 1. Пока у заявки нет связи с продуктами (это Этап 4), бери поля `it_program`/`it_product` из заявки как есть и пометь в отчёте.

**Тесты:**
- xlsx открывается `openpyxl`, строки совпадают с видимостью каждой роли;
- pdf не пустой, начинается с `%PDF`;
- неверная колонка даёт 422.

### Задача 5. Рекомендации продуктов вузу (Этап 6, прототип)

**Что нужно.** Новый модуль `src/quoll/recommendations/`: чистая функция в `policy`, без БД, плюс эндпоинт `GET /api/v1/recommendations/universities/{id}?limit=`.

**Алгоритм детерминированный**, по рекомендации 6.1: пересечение ключевых слов программ вуза (`disciplines` + `keywords` из задачи 1) и `keywords` продукта. Нормализация: нижний регистр, `ё` → `е`, простая лемматизация или стемминг без тяжёлых зависимостей. Мера — Jaccard или TF-IDF.

**Уровень совпадения** по разбору аналитика, шаг 0:
- «полное» — можно внедрять;
- «частичное» — нужно доп. обучение преподавателей;
- «слабое» — предложить другие продукты.

Пороги — константы в одном месте.

**Ответ:** продукты по убыванию оценки, у каждого — уровень и совпавшие слова, чтобы руководитель видел, почему. Видят руководитель и админ.

**Тесты:** чистой функции — на таблице примеров; эндпоинта — права и сортировка.

### Задача 6. Заглушка интеграции с сайтом вуза и LMS (ТЗ п. 5, «можно на заглушках»)

**Что нужно.** Модуль `src/quoll/integrations/`:
- интерфейс `UniversitySource.fetch_programs(university)` и `fetch_contacts(university)` → JSON;
- реализация-заглушка читает JSON-фикстуры из `backend/seed/integrations/*.json`;
- эндпоинт админа `POST /api/v1/integrations/universities/{id}/sync` — кладёт данные в `university_programs` и `university_contacts` из задачи 1: upsert, помеченный источником `source='website'|'lms'`.

**Не делай:** ничего не пиши в заявки и воркфлоу — «добавление в существующий или новый workflow» появится позже. Опиши, как видишь это место, в отчёте.

**Тесты:** идемпотентность повторной синхронизации; битый JSON даёт понятную ошибку и откатывает всё.
