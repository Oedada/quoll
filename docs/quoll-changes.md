# Что изменилось в бэкенде

Отчёт для того, кто видел код до этих правок: что появилось, как устроено внутри и почему сделано именно так.

## Словарь

Понятия, которые дальше используются без пояснений.

> **Воркфлоу** — маршрут, по которому движется работа с вузом. В ТЗ он описан как
> последовательность из 14 шагов: от поиска контактного лица до повышения квалификации
> преподавателей. Хранится в таблице `workflows`.

> **Стадия** (`stages`) — один шаг этого маршрута: «Встреча», «Подписание договора»,
> «Передача материалов». У стадии есть позиция в маршруте и два флага, которые определяют,
> как она влияет на нагрузку менеджера (см. ниже). Стадии принадлежат конкретному воркфлоу.

> **Переход** (`workflow_transitions`) — разрешённое ребро между стадиями: откуда куда можно
> двигаться. Переход с пустым `from_stage_id` означает вход в маршрут.

> **Заявка**, она же взаимодействие (`interactions`) — конкретная работа с конкретным вузом по
> конкретному продукту. Едет по стадиям воркфлоу, имеет ответственного менеджера, может
> вставать на паузу.

> **Роли.** *Менеджер* ведёт заявки. *Руководитель* распределяет менеджеров и следит за ними.
> *Администратор* занимается справочниками, правами и настройками, но бизнес-действий не
> совершает — не двигает заявки и не согласует переходы.

> **Слот, ёмкость** — у менеджера есть потолок одновременных заявок (по умолчанию 5). Каждая
> заявка, находящаяся в работе, занимает один слот. Сколько именно слотов занято — считается по
> правилу, описанному в разделе про ёмкость.

> **Проекция пользователей** — локальная копия учётных записей Keycloak в нашей таблице `users`.
> Keycloak остаётся источником правды о том, кто существует и какая у него роль; наша база —
> о том, чем он владеет и насколько загружен.

> **Инвариант** — правило, записанное в самой базе (внешний ключ, `CHECK`, триггер, уникальный
> индекс). Его нельзя обойти ни из кода, ни руками через psql.

> **Блокировка строки** — `SELECT ... FOR UPDATE`: «беру эту строку себе до конца транзакции,
> остальные ждут». Нужна, чтобы две параллельные операции не затёрли друг друга.

## Проекция пользователей: что было и что стало

Таблица `users` с тремя подтипами существовала и раньше. Но проекцией в рабочем смысле она не
была, по трём причинам.

**Логин и почта не были колонками.** В модели стояло:

```python
__allow_unmapped__ = True
username: str | None = None      # обычный атрибут класса,
email: str | None = None         # а не mapped_column
```

Эти поля жили только в памяти, и чтобы их заполнить, `UserRepository.get()` ходил в Keycloak по
HTTP. А `get_current_user` вызывал именно его — значит, сетевой поход случался на **каждом**
запросе к API.

**Таблица лежала в отдельном наборе метаданных.** `User` наследовался от `RawBase`, всё
остальное — от `Base`. Для SQLAlchemy это два несвязанных набора таблиц, и внешний ключ из
`interactions` на `managers` поставить было нельзя. То есть главное, ради чего нужна локальная
копия, не работало.

**Строки подтипов не создавались.** Эндпоинт создания пользователя конструировал голый
`User(...)`. При наследовании «одна таблица на класс» это кладёт строку в `users` и не создаёт
парную строку в `managers`. Дальше такой объект падает при первом же обращении к полям подтипа.

### Что сделали

| | Было | Стало |
| :--- | :--- | :--- |
| `username`, `email` | атрибуты в памяти, из Keycloak на каждый запрос | колонки `String(255)` с индексом |
| Базовый класс | `RawBase`, отдельные метаданные | общий `Base` — внешние ключи заработали |
| Создание | голый `User`, подтип не появлялся | `user_class_for_role(role)` + проверка в репозитории |
| Активность | отличить уволенного было нечем | `is_active`, по умолчанию `false` |
| Расхождение с Keycloak | не отслеживалось | `identity_sync_status`, `role_transition_status` |
| Нагрузка | полей не было | `max_active_projects`, `manual_workload_status`, `max_subordinates` |
| Удаление подтипов | `ON DELETE CASCADE` | `ON DELETE RESTRICT` |
| `managers.superviser_id` | `SET NULL` | `RESTRICT` |
| Хранение роли | `MANAGER` | `manager` |
| Время изменения | не было | `created_at`, `updated_at` + триггер |

**Про регистр роли.** `Mapped[UserRole]` по умолчанию пишет в базу *имя* члена перечисления, то
есть `MANAGER`. Весь SQL оргструктуры сравнивает роль со строкой `'manager'`, и такие запросы
молча возвращали бы пусто. Лечится параметром при объявлении колонки:

```python
role: Mapped[UserRole] = mapped_column(
    SAEnum(UserRole, name="userrole",
           values_callable=lambda enum: [member.value for member in enum]),
    index=True,
)
```

**Про `user_class_for_role`.** Функция возвращает конкретный класс по роли, а репозиторий при
создании дополнительно проверяет, что переданный объект этому классу соответствует. Две проверки
на одно правило — потому что нарушение тихое: строка ляжет в базу, а сломается всё гораздо позже.

## Новые таблицы

### `sessions` — переписана

Было четыре колонки: `id`, `user_id`, `access_token`, `refresh_token`, всё открытым текстом.

Стало:

| Колонка | Тип | Зачем |
| :--- | :--- | :--- |
| `id` | `String(64)` | `sha256` от ключа, выданного клиенту |
| `user_id` | `String(255)`, индекс | Сессии массово отзываются по пользователю |
| `refresh_token` | `Text` | Зашифрован, см. раздел про сессии |
| `created_at` | `timestamptz` | |
| `expires_at` | `timestamptz`, индекс | Срок жизни, берётся из ответа Keycloak |
| `last_validated_at` | `timestamptz` | Когда последний раз сверялись с Keycloak |

Внешнего ключа на `users` намеренно нет: сессия создаётся сразу после входа, а локальная строка
пользователя может появиться позже — её заводит фоновая сверка.

### `audit_logs` — новая

Журнал действий: кто, что, над кем, когда, что было и что стало. Нужен по требованиям
безопасности из ТЗ.

| Колонка | Зачем |
| :--- | :--- |
| `actor_type` | `USER` или `SYSTEM` — человек или фоновый процесс |
| `actor_id` | Кто сделал; у системных записей всегда пусто |
| `target_type`, `target_id` | Над кем или над чем |
| `event_type` | Что именно произошло, 24 значения |
| `old_value`, `new_value` | `JSONB` — состояние до и после |
| `created_at` | Индексируется, по нему ищут |

Колонки `updated_at` нет и не будет: записи не меняются. Это не договорённость, а триггер в
базе — любой `UPDATE`, `DELETE` или `TRUNCATE` завершается ошибкой.

Сейчас в неё ещё никто не пишет: писатели появятся вместе с операциями оргструктуры.

### `pending_org_actions` — новая

Очередь дел, которые нельзя сделать прямо сейчас.

> **Зачем очередь.** Сотрудника уволили в Keycloak, но за ним висят три заявки. Удалить его
> нельзя — заявки осиротеют. Оставить как есть тоже нельзя. Значит, кладём задачу в очередь, и
> фоновый процесс будет к ней возвращаться, пока руководитель не разберёт заявки. Очередь именно
> в базе, а не в памяти: между постановкой задачи и её выполнением могут пройти недели и
> несколько перезапусков приложения.

Три типа задач: `OFFBOARDING_MANAGER` (уволился менеджер), `OFFBOARDING_SUPERVISER` (уволился
руководитель, надо пристроить его подчинённых), `ROLE_TRANSITION` (сменилась роль, надо перенести
человека в другую таблицу подтипа).

Задачу будет брать фоновый процесс, и чтобы два процесса не взялись за одну, есть **аренда**:

| Колонка | Зачем |
| :--- | :--- |
| `worker_id` | Кто взял задачу |
| `lease_until` | До какого момента она за ним закреплена |
| `lease_version` | Номер поколения аренды, растёт при каждом захвате |
| `retry_count`, `max_attempts` | Счётчик попыток при технических сбоях |
| `next_retry_at` | Когда пробовать снова |
| `last_error` | Текст последней ошибки |

> **Зачем `lease_version`.** Процесс может зависнуть — например, машину усыпили. Он очнётся через
> час, когда задачу давно перехватил и выполнил другой. Если бы он просто записал результат, то
> затёр бы чужую работу. Поэтому при записи он обязан предъявить тот номер поколения, с которым
> брал задачу; за это время номер уже вырос, и запись не пройдёт.

### Что добавилось к существующим таблицам

**`interactions`:**

- `owner_id` теперь ссылается на `managers.id`, а не просто хранит строку. Назначить владельцем
  заявки руководителя или администратора физически невозможно.
- `last_owner_id` → `users.id` — кто владел раньше. Когда менеджера переводят на другую должность,
  строка из `managers` исчезает, а авторство должно остаться.
- `is_paused`, `pause_state`, `paused_until` — состояние паузы.

> **Четыре состояния паузы.** `ACTIVE` — работа идёт. `PAUSED_MANUAL` — остановлена без срока
> (вуз попросил подождать). `PAUSED_TIMED` — остановлена до конкретной даты. `EXPIRED_WAITING_CAPACITY`
> — срок вышел, но вернуть заявку в работу нельзя: у менеджера нет свободного слота. Последнее
> состояние нужно, чтобы заявка не потерялась и её было видно в отчётах.

**`stages`** — два флага, которые и определяют влияние стадии на нагрузку:

- `is_terminal` — стадия завершает работу (договор закрыт, либо отказались);
- `consumes_capacity` — стадия занимает слот менеджера.

> **Почему два флага, а не один.** Есть стадии, которые формально в работе, но внимания почти не
> требуют — например, ожидание ответа от вуза. Их можно пометить как не занимающие слот, и менеджер
> сможет взять ещё одну заявку. Терминальная стадия слот не занимает по определению, поэтому
> сочетание «завершена и занимает» запрещено ограничением в базе.

**`workflows`** — `is_published`. Пока маршрут не опубликован, стадии можно менять; после публикации
структура фиксируется, потому что по ней уже едут живые заявки.

## Инварианты в базе

| Что запрещено | Чем | Имя |
| :--- | :--- | :--- |
| Сделать владельцем заявки не менеджера | Внешний ключ на `managers` | `fk_interactions_owner_id_managers` |
| Удалить менеджера с заявками | `ON DELETE RESTRICT` | там же |
| Поставить заявку на стадию чужого воркфлоу | Составной внешний ключ | `fk_interactions_state_id_workflow_id_stages` |
| Указать стадию, не указав воркфлоу | `CHECK` | `chk_interaction_stage_requires_workflow` |
| Рассогласовать поля паузы | `CHECK` на 4 комбинации | `chk_interaction_pause_state` |
| Завершающая стадия занимает слот | `CHECK` | `chk_stage_terminal_no_capacity` |
| Системная запись журнала с автором | `CHECK` | `chk_audit_actor_invariants` |
| Изменить или удалить запись журнала | Триггер | `trg_audit_logs_append_only_guard` |
| Устаревшая метка времени при прямом `UPDATE` | Триггер | `trg_users_updated_at` |
| Две активные задачи одного типа на человека | Частичный уникальный индекс | `uq_active_pending_org_action` |

Два места заслуживают пояснения.

**Составной ключ на стадию.** У заявки есть и `workflow_id`, и `state_id`, и ничто не мешало
поставить заявку воркфлоу A на стадию из воркфлоу Б. Чтобы это запретить, на `stages` добавлена
уникальность пары `(id, workflow_id)` — она дублирует первичный ключ, но нужна как цель ссылки, —
а `interactions` ссылается на эту пару целиком. Тонкость: составной ключ не проверяется, если
хотя бы одна колонка пуста. Поэтому рядом стоит `CHECK`: стадия без воркфлоу недопустима.
А вот воркфлоу без стадии — нормальный случай, это черновик, которому уже выбрали маршрут.

**Частичный уникальный индекс.** Задачи из очереди не удаляются, они переходят в `COMPLETED` или
`CANCELLED` и лежат вечно. Обычная уникальность по паре «тип, пользователь» запретила бы повторный
цикл: человека уволили, потом взяли обратно, потом снова уволили. Поэтому индекс сужен условием
`WHERE status IN ('PENDING', 'IN_PROGRESS')` — уникальны только активные задачи.

Все инварианты покрыты тестами: в `tests/test_schema_invariants.py` видно, как каждый срабатывает.

## Механизм 1: сессии

### Вход

1. Пользователь идёт на `/auth/`, его перекидывает в Keycloak.
2. Keycloak возвращает его на `/auth/callback` с кодом.
3. Меняем код на токены.
4. Генерируем случайный ключ: `secrets.token_urlsafe(64)`. **Клиенту в куку уходит сам ключ,
   в базу пишется его `sha256`.**
5. Refresh-токен шифруем и кладём в базу.
6. Access-токен не сохраняем вовсе.

> **Почему в базе хеш.** Если база утечёт, по хешам чужие сессии не восстановить — тот же приём,
> что с паролями. Ключ на 64 байта перебрать нереально, а сравнение по хешу ничем не медленнее.

> **Почему access-токен не нужен.** Он живёт пять минут. Роль и статус мы берём из своей таблицы
> `users`, а не из токена, поэтому хранить его незачем. Refresh-токен, наоборот, нужен: им
> выходят из Keycloak и им же сверяются.

Кука ставится с флагами `httponly`, `samesite=lax`, `path=/`, сроком по времени жизни сессии и
`secure` из настройки `SESSION_COOKIE_SECURE` — её выключают только для локальной разработки
по http.

### Шифрование

Refresh-токен шифруется Fernet из библиотеки `cryptography`, ключ берётся из
`SESSION_SECRET_KEY`. Можно указать несколько ключей через запятую: шифрование идёт первым,
расшифровка — любым. Это даёт смену ключа без разлогина всех разом.

Fernet выбран вместо голого AES-GCM намеренно: последний требует вручную управлять одноразовым
числом, а ошибка в этом месте обесценивает шифрование целиком.

Если расшифровать не удалось — ключ потеряли или сменили без переходного периода — сессия
закрывается, и человек просто входит заново. Не 500 на каждом запросе.

### Проверка на каждом запросе

Сессия ищется одним запросом:

```sql
SELECT ... FROM sessions WHERE id = :хеш AND expires_at > now()
```

Срок проверяет сама база. Это не экономия строчки: при отдельной проверке в коде между «проверили»
и «использовали» остаётся промежуток, в который сессия может истечь.

Дальше смотрим на `last_validated_at`:

| Прошло | Что делаем |
| :--- | :--- |
| меньше 300 с | В Keycloak не ходим |
| больше 300 с | Идём сверяться |
| больше 900 с без успешной сверки | Закрываем сессию |

Оба порога настраиваются: `SESSION_REVALIDATE_SECONDS` и `SESSION_REVALIDATE_HARD_LIMIT_SECONDS`.

### Сверка

Сверка — это попытка обновить токен через Keycloak. Она отвечает сразу на три вопроса: жива ли
сессия в Keycloak, не заблокировали ли человека, не сменили ли ему роль. Если Keycloak обновил
токен — всё в порядке.

| Исход | Что делаем |
| :--- | :--- |
| 200 | Сохраняем новый refresh-токен, продлеваем срок сессии |
| 4xx | Сессию отозвали или человека заблокировали — удаляем сессию, 401 |
| Сеть не ответила за 3 с | Сессию не трогаем, но возвращаем метку времени назад |

Последняя строка важна. Захват сверки сдвигает `last_validated_at` вперёд ещё до похода в сеть.
Если бы при сбое мы этот сдвиг оставили, получилось бы, что сверка «прошла», и отсчёт до
жёсткого лимита обнулился — сессия пережила бы упавший Keycloak навсегда. Поэтому метка
возвращается на прежнее значение, и окно в 900 секунд продолжает идти.

Заодно из ответа достаются claims и сверяется роль с локальной проекцией. Расхождение пока только
пишется в лог: решения принимаются по базе, а не по токену.

### Почему не на каждом запросе

Тогда каждый клик уходил бы в Keycloak, а его падение останавливало бы работу целиком. Раз в пять
минут — компромисс: заблокированный сотрудник теряет доступ максимум через пять минут.

### Параллельные запросы

Браузер на одном экране шлёт пять-десять запросов разом. Если все они увидят «пора сверяться», то
все пойдут обновлять токен. А если в Keycloak включён одноразовый refresh-токен, каждый следующий
обнулит предыдущий, и сессия умрёт на ровном месте.

Поэтому перед походом в сеть запрос пытается застолбить сверку:

```sql
UPDATE sessions SET last_validated_at = now()
WHERE id = :хеш AND last_validated_at = :то_что_я_видел
RETURNING id
```

Строка обновится только у одного — он и пойдёт в Keycloak. Остальные работают как есть: их данные
всё равно свежие в пределах интервала.

> **Почему хранилище сессий работает на своих транзакциях.** Захват должен стать видимым соседним
> запросам немедленно. Если бы он висел в незакоммиченной транзакции запроса, соседи его бы просто
> не увидели, и вся затея не работала бы. Поэтому `SessionStore` открывает короткую транзакцию на
> каждую операцию, независимо от транзакции запроса. Побочный плюс: отзыв сессии не откатится
> вместе с какой-нибудь бизнес-ошибкой.

### Сроки

Срок сессии берётся из поля `refresh_expires_in` ответа Keycloak и продлевается при каждой сверке.
Это и есть таймаут простоя, заданный политикой провайдера, — свой параллельный таймер заводить не
пришлось.

Считаем по относительным значениям, а не по абсолютной дате внутри токена: так расхождение часов
между нашим сервером и Keycloak ни на что не влияет. Плюс тридцать секунд запаса.

## Механизм 2: блокировки строк

### Задача

Два руководителя одновременно назначают заявки одному менеджеру, у которого свободно одно место.
Оба прочитали «занято 4 из 5», оба решили, что место есть, оба записали — стало 6.

Лечится блокировкой: первый берёт строку менеджера себе, второй ждёт, дожидается, видит уже 5 из 5
и получает отказ.

### Порядок

Если одна операция берёт сначала строку А, потом Б, а другая — сначала Б, потом А, они встанут
намертво: каждая ждёт ту, которую держит другая. База такое замечает и убивает одну из транзакций.

Лечится единым порядком для всех:

```
Superviser → Manager → User → Interaction → PendingOrgAction → Workflow → Stage
```

А если на одном уровне несколько строк — по возрастанию `id`.

### Ловушка

Казалось бы, достаточно написать `select(Manager).with_for_update()`. Но `Manager` — наследник
`User`, и такой запрос разворачивается в:

```sql
SELECT ... FROM users JOIN managers ON users.id = managers.id ... FOR UPDATE
```

Блокируются **обе** строки, причём `users` раньше `managers` — ровно наоборот установленному
порядку. Код, написанный «в лоб», ломал бы правило, ради которого всё затевалось.

### Решение

Модуль `core/locking.py` с двумя функциями:

```python
async def lock_row(session, model, ident):
    stmt = (
        select(model)
        .where(model.id == ident)
        .with_for_update(of=model.__table__)   # ключевое место
    )
    return (await session.execute(stmt)).scalar_one_or_none()
```

`FOR UPDATE OF <таблица>` блокирует строки только названной таблицы. Запрос по-прежнему делает
`JOIN`, но под замок попадает ровно одна нужная строка.

`lock_rows` берёт несколько строк одного уровня **отдельными запросами** по возрастанию `id`.
Не одним запросом с `IN (...) ORDER BY id`, потому что тогда порядок захвата определял бы
планировщик базы, а не наш код. Ради двух-трёх строк это допустимая цена.

Любой `FOR UPDATE` в проекте должен идти через эти функции. Тесты в `tests/test_locking.py`
проверяют в том числе, что блокировка `managers` действительно не задевает `users`: одна
транзакция держит строку менеджера, вторая в это же время свободно берёт строку пользователя.

## Механизм 3: сколько заявок тянет менеджер

### Правило

Функция `counts_toward_capacity(stage, is_paused)`. Слот занимается, только если выполнено всё
сразу:

- стадия у заявки задана — черновик без стадии места не занимает;
- стадия не завершающая;
- у стадии стоит `consumes_capacity`;
- заявка не на паузе.

### Три счётчика

Их легко перепутать, а считают они разное:

| Функция | Что считает | Где нужна |
| :--- | :--- | :--- |
| `count_capacity_projects` | Занятые слоты | Проверка перед назначением |
| `count_open_projects` | Незакрытые заявки, включая паузы | Отчёты, витрины |
| `count_owned_nonterminal_interactions` | То же плюс черновики без стадии | Можно ли отпустить менеджера |

Третий — самый строгий. Пока он не ноль, менеджера нельзя открепить от руководителя и нельзя
завершить смену его роли: иначе заявки останутся без ответственного.

Правило описано один раз и используется дважды: как функция на Python для доменной логики и как
SQL-выражение для выборок. Второе — чтобы не вытаскивать все заявки в память ради подсчёта.

### Страж

Перед тем как повесить на менеджера ещё одну заявку, вызывается
`validate_capacity_transition(session, manager, delta_slots)`:

| Проверка | Отказ |
| :--- | :--- |
| `delta_slots` больше нуля? | Если нет — пропускаем без проверок |
| Сотрудник активен? | 400 |
| Готов брать новое (`manual_workload_status`)? | 400 |
| Хватает свободных слотов? | 409 |

Первая строка не формальность. Если нагрузка не растёт — например, заявку наоборот закрывают, —
проверки пропускаются. Иначе недоступный менеджер не смог бы закрыть собственную заявку.

Страж имеет смысл только если строка менеджера уже заблокирована: иначе между подсчётом и записью
влезет кто-то ещё. Это записано в его документации, а сам захват оставлен вызывающему коду —
потому что порядок блокировок важен именно там, где он берётся.

## Миграции

Схема больше не создаётся при старте приложения — за неё отвечает Alembic. Сейчас одна миграция,
создающая всё сразу.

Автогенерация не видит триггеры, поэтому их блок дописан в конце файла руками. Там же лежит
удаление типа перечисления `userrole`: `drop_table` его не снимает, и без этого повторный
`upgrade` падает.

Продакшена нет, базу можно пересоздавать, поэтому цепочку ревизий не копим. При изменении моделей:
`alembic downgrade base`, удалить файл ревизии, сгенерировать заново, перенести блок триггеров.

Именование ограничений задано конвенцией на уровне метаданных — без неё автогенерация выдавала
безымянные `drop_constraint`, которые просто не выполняются.

Запуск с нуля:

```bash
uv sync --all-groups
docker compose up -d
uv run alembic upgrade head
uv run uvicorn quoll.main:app --reload
```

Тесты поднимают отдельную базу `quoll_test_db` и накатывают на неё те же миграции, так что
миграция проверяется на каждом прогоне.

## Заведение администратора

Раньше администратор приходил из импорта realm Keycloak. Теперь его создаёт приложение при старте
(`auth/bootstrap.py`). Две ветки:

- учётки в Keycloak нет — создаём её, идентификатор выдаёт Keycloak, по нему заводим локальную
  строку;
- учётка есть, а локальной строки нет — например, пересоздали базу — находим по логину и
  восстанавливаем строку с тем же идентификатором.

Вторая ветка существует потому, что без неё после пересоздания базы администратор не мог бы войти:
в Keycloak он есть, в проекции его нет, и `get_current_user` отдаёт 401.

Если Keycloak недоступен, пишем ошибку в лог, но приложение всё равно стартует: иначе порядок
запуска контейнеров превращался бы в лотерею.
